# v2.6.0 部署手册

> **这份是 [v2.5.0 部署手册](./v2.5.0-deploy.md) 的增量，不是替代。**
>
> v2.5.0 那份 818 行里，env 校验、compose 拓扑、备份、HTTPS、OTP 通道、监控、
> 联系人这些章节这次一个字都没变。把它们抄一遍只会产生第二份会烂掉的副本——
> v2.4.0 → v2.5.0 就是这么留下一份停在 migration 020 的手册的。
>
> **所以：先从头到尾过一遍 v2.5.0 那份，再回到这里。** 下面只写本次新增或
> 改变的东西，以及 v2.5.0 那份里已经不再正确的地方。
>
> 通用门禁仍在 [`docs/release-checklist.md`](../release-checklist.md)。

## 0. 这次发了什么

三块新东西，外加一批修正。

1. **临床试验数据是活的了。** `trial_records` 由定时任务从 ClinicalTrials.gov
   刷新，不在请求路径上。问答层不再只能从建库时的语料回答「有没有在招的试验」。
2. **管理员后台。** 对患者档案全量可读写，读也审计。角色不能自助获取。
3. **重新征求同意。** 隐私政策因为第 2 条实质变更，版本号已 bump——**上线后每个
   活跃账号下次打开都会先看到一屏同意页**。这不是 bug，见 §5。

还有一件事本次**没有**做，运维需要知道：**患者点「暂不同意」并不会阻止管理员读他的
档案。** API 里没有任何地方把管理员访问和这个同意台账挂钩。同意页没有声称它能挡住
（有测试钉着那句话不许出现），但这是个待法务确认的问题，不是已经解决的问题。

## 1. 相对 v2.5.0 的破坏性变化

### 1.1 ⛔ 数据库要从 020 一路跑到 027，中间有两条不可逆

v2.5.0 手册的 §2.1 标题写的是「数据库迁移（013 → 020）」，仓库里现在有到 **027**。

**这份手册不知道你的生产库停在哪一条**，也不要去猜——上一版手册写到 020 只说明
写它的时候仓库里最新是 020，不说明生产库现在就在 020。先问库自己（命令与
v2.5.0 §2.1 完全相同，在宿主机上跑）：

```bash
npm run db:migrate:status
```

> 这条走 `tsx`，是 devDependency。**宿主机必须是完整 `npm ci`，不能是 `--omit=dev`。**
> 生产镜像里没有 tsx，所以这条不能在容器里用 `npm run` 跑。

它报 `applied / pending / drifted / orphan` 四态。两件事要现在就分清：

- **`drifted` 不拦截，也基本不用管。** 本仓库 019 和 022 的磁盘文件在应用之后
  被改过，改的全是注释（022 另有一处 `RAISE NOTICE` → `RAISE WARNING`，只影响
  日志级别）。ledger 里记的是当时的 SHA-256，对不上是预期内的。**已经跑过 022
  的库不会再跑它**，所以那处 WARNING 提升对存量库无效——022 文件自己写了这件事。
- **`orphan` 会让命令非零退出，必须处理。** 见 v2.5.0 §2.1 的 pre-flight。

下面这张表覆盖 021–027。你的库里已经是 `applied` 的行跳过就行；`pending` 的按
顺序跑。

| 迁移 | 做什么                                                       | 回滚               |
| ---- | ------------------------------------------------------------ | ------------------ |
| 021  | `passport_share_links`                                       | 建表，`_down` 删表 |
| 022  | `instruments` + `instrument_administrations`                 | `_down` 10 条语句  |
| 023  | `patient_falls`                                              | 建表               |
| 024  | `passport_pickup_codes`                                      | 建表               |
| 025  | 重建 `idx_patient_measurements_cohort`（加 `profile_id`）    | 见下               |
| 026  | `trial_records` + `trial_fetch_runs` + `audit_logs` 复合索引 | 建表               |
| 027  | `trial_fetch_runs.source_reported_total` 等列                | 删列               |

**025 是本批唯一一条 `DROP INDEX` 在前的迁移。** 它先删掉 018 建的
`idx_patient_measurements_cohort`，再用带 `profile_id` 的列序重建。回滚 025 会把
索引恢复成 018 的形态——但如果在 025 已应用的库上直接回滚到 018 之前，018 的
ledger 行还在而索引已经是 025 的形态了。**回滚必须严格倒序**，不要跳。

**回滚到 021 之前会永久丢数据**：021/024 的分享链接与取件码、022 的量表作答、
023 的跌倒记录，`_down` 都是 `DROP TABLE`。这些是患者自己录进去的东西，不是可以
重算的派生数据。回滚前先按 v2.5.0 §1.7 做一次备份，并且**确认那次备份真的落盘了**
（`ls -l` 看大小，不要只看命令退出码）。

### 1.2 ⛔ 反代要放行 `/s/*`，否则分享链接 404

临床护照的分享页挂在 `/s/passport/:token`，**在 `/api` 之外**。v2.5.0 的 Caddy
配置只有 `handle /api/*` 和一个 catch-all 到前端静态站，所以这个路径会被前端
路由接走，患者拿到的是「这个链接打不开了」。

本次仓库里的 `Caddyfile` 和 `apps/mobile/nginx.conf` 都已加好，但**生产机上的
Caddyfile 如果是手工维护的副本，要自己同步这一段**：

```
handle /s/* {
    reverse_proxy api:4000
}
```

放在 catch-all 之前。nginx 那份对应 `location /s/ { proxy_pass http://api:4000/s/; }`。

验证（`scripts/smoke-test.sh` 里也有这条）：一个不存在的 token 必须返回
**404 且是 API 自己的页面**。如果返回 200，说明请求被前端接走了，配置没生效——
这条正是因为 200 和 404 在这里长得都像「正常」才写成断言的。

### 1.3 生产镜像新增一个文件

`apps/api/Dockerfile` 现在会 `COPY scripts/admin-role.mjs`。原因见 §3.1：
第一个管理员必须在跑着的生产栈上产生，而在 psql 里手写 `UPDATE app_users` 会丢掉
脚本在同一事务里写的 `audit_logs` 行。

这意味着**必须重新 build 镜像**，不能只 `docker compose up -d` 拉旧镜像。

## 2. 定时任务：试验数据刷新（新增，要在宿主机配）

刷新**不在**请求路径上，也**不在** compose 里。它是宿主机 cron。不配它，
`trial_records` 会一直停在你导入时的那一份，患者看到的 `fetched_at` 会越来越旧
（页面会如实显示这个时间，不会假装是新的）。

生产镜像里没有 `tsx`（`npm ci --omit=dev`），所以 **`npm run trials:refresh` 在
生产上跑不了**。跑编译产物：

```bash
17 * * * * cd /srv/openrd && flock -n /tmp/openrd-trials.lock docker compose exec -T api node dist/modules/trials/refresh.cli.js >> /var/log/openrd/trials.log 2>&1
```

- `flock` 是为了慢抓取不与下一次重叠。
- **注意这条把 stderr 重定向进了日志文件，所以 cron 不会发邮件。** 失败的完整原因
  在 `/var/log/openrd/trials.log`；`trial_fetch_runs.error` 里存的是截断版，两者
  不是同一个字符串。要靠邮件告警就去掉 `2>&1` 那段重定向，自己决定。
- 退出码只有在**每个**源都成功时才是 0。部分成功退出 1。
- 第一次手动跑一遍再进 cron，确认出站网络能到 clinicaltrials.gov。

**国内注册库（chinadrugtrials.org.cn）当前返回 0 条 FSHD 试验，这是注册库自己的
答案，不是抓取失败。** 它对第一次请求返回 202（反爬），随后 200 + 共 0 条记录。
数据里这两种情况是分开记的，页面上也分开显示——看到「0 条」不要当成任务坏了。

## 3. 管理员账号

### 3.1 第一个管理员怎么来

角色不能自助获取：注册接口的枚举里没有 `admin`，没有任何 API 能提升自己。只能从
运维侧给：

```bash
docker compose exec api node /app/scripts/admin-role.mjs grant <phone>
```

- **是 `exec`，不是 `exec -T`。** 脚本要在终端上读一次确认；`-T` 拿掉终端后它会
  在开事务之前就拒绝执行，什么都不改。
- 账号必须**已经注册过**。脚本不建账号。
- 手机号带不带 `+86` 都行，两种形态都会查。
- 角色变更和 `audit_logs` 行在同一个事务里写。

撤销是 `revoke`。**撤销立即生效**——角色是每个请求现查数据库的，不是从 token 里
读的，所以不用等对方的登录态过期。

### 3.2 上线后要核对的一件事

```sql
SELECT id, phone_number, role FROM app_users WHERE role = 'admin';
```

这张表应该只有你自己刚授的那些。如果有意料之外的行，先 revoke 再查
`audit_logs`（`event_type` 上本次新加了复合索引，查得动）。

### 3.3 审计表会长

`audit_logs` 现在也记**读**——管理员看一次患者档案就是一行。这是设计，不是冗余：
在这个后台里，「谁看了谁」才是要紧的事件。026 给 `(event_type, occurred_at)` 建了
复合索引。留存期 180 天，清理逻辑沿用既有的 purge。

## 4. 上线顺序（相对 v2.5.0 §3.2 的差异）

v2.5.0 §3.2 的顺序照旧，插入两步：

1. 备份（**确认落盘**，见 §1.1）
2. `git checkout` + `.env` 补齐（v2.5.0 §1.0-0 那个顺序陷阱仍然成立）
3. **同步反代的 `/s/*` 段**（§1.2）—— 放在 build 之前，因为它要跟着 reload
4. `docker compose --profile prod build`（**必须 build，见 §1.3**）
5. `up -d`
6. 迁移：先 `npm run db:migrate:status` 看库停在哪，再 `npm run db:migrate`（§1.1）
7. `docker compose exec api node /app/scripts/admin-role.mjs grant <你自己的手机号>`
8. **配 cron（§2），并手动跑一次**
9. 冒烟测试 `scripts/smoke-test.sh`（含 `/s/` 那条断言——相对上一次部署是新的）

## 5. 上线后第一件会发生的事：所有人看到同意页

隐私政策版本 bump 了，所以**每个活跃账号下次打开 App 都会先进一屏「有条款需要你
确认」**。这是 §9 承诺过的，不是故障。

盯这几件事：

- 客服/群里会收到「怎么突然要我同意」的问题。同意页第一屏就写了变了什么
  （管理员可以查阅和代填档案），可以直接引用那几句。
- **Web export 和 API 是分开发布的。** 如果只更新了 API 而前端还是旧 bundle，
  服务端会说「有个版本要确认」而旧 bundle 显示不出来。这个死循环代码里挡掉了
  （存的同意版本等于当前 bundle 版本时跳过），但**正确的做法仍然是两个一起发**。
- 点「暂不同意」的人不会被踢出去，也不会被限制功能——见 §0 最后那段。

## 6. v2.5.0 手册里已经不再正确的地方

- **§2.1 标题「013 → 020」**：生产这次要跑到 027。
- **§4.1 回滚表**：只列到 020。021–027 的回滚见本文 §1.1，其中回滚到 021 之前
  会永久丢患者数据。
- **反代章节（§1.5）**：只有 `/api/*`，缺 `/s/*`。见本文 §1.2。
- **§3.5 全新部署的 KB seed**：步骤本身没变，但语料在本次之后应重新 ingest，
  否则问答里的知识库部分与 `trial_records` 的时间基准不一致（不影响可用性）。

## 7. 已知关注点

- **「暂不同意」不改变任何事**（§0）。待法务确认。
- **本次改动没有在真机微信浏览器里跑过。** 测试驱动的是控制器吐出的响应形态。
  前端以 web export 形式在微信 X5 内核里打开，这层没有覆盖到——上线后第一时间
  自己用微信打开一遍分享链接和同意页。
- `source_reported_total` 记录了但目前没有任何界面读它。
