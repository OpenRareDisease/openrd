## 0. 这次发了什么

三块新东西，外加一批修正。

1. **临床试验数据是活的了。** `trial_records` 由定时任务从 ClinicalTrials.gov
   刷新，不在请求路径上。问答层不再只能从建库时的语料回答「有没有在招的试验」。
2. **管理员后台。** 患者名单、单个患者的档案（账号、身份、基线，以及报告 / 随访 /
   跌倒 / 量表这几段历史）、单人导出与全量 CSV 导出，外加只读的运维视图
   （`/ops/corpus`、`/ops/parse-failures`、`/ops/ai-usage`、`/ops/health`）。
   **写只有一条路**：`PUT /patients/:userId/baseline`，而且只认
   `ADMIN_WRITABLE_BASELINE_FIELDS` 这张白名单上的字段，改到清单外的字段返回 400
   并点名是哪个。读也审计。角色不能自助获取。
3. **重新征求同意。** 隐私政策因为第 2 条实质变更，版本号已 bump——**上线后每个
   活跃账号下次打开都会先看到一屏同意页**。这不是 bug，见 §5。

还有一件事本次**没有**做，运维需要知道：**患者点「暂不同意」并不会阻止管理员读他的
档案。** API 里没有任何地方把管理员访问和这个同意台账挂钩。同意页没有声称它能挡住
（有测试钉着那句话不许出现），但这是个待法务确认的问题，不是已经解决的问题。

## 1. 相对 v2.5.0 的破坏性变化

### 1.1 ⛔ 数据库要从 020 一路跑到 027；021–024 的回滚会永久删患者数据

v2.5.0 手册的 §2.1 标题写的是「数据库迁移（013 → 020）」，仓库里现在有到 **027**。

**这份手册不知道你的生产库停在哪一条**，也不要去猜——上一版手册写到 020 只说明
写它的时候仓库里最新是 020，不说明生产库现在就在 020。先问库自己（在宿主机上跑）：

```bash
DATABASE_URL=postgres://<角色>:<密码>@127.0.0.1:5432/fshd_openrd npm run db:migrate:status
```

> 这条走 `tsx`，是 devDependency。**宿主机必须是完整 `npm ci`，不能是 `--omit=dev`。**
> 生产镜像里没有 tsx，所以这条不能在容器里用 `npm run` 跑。
>
> **必须在 `up -d` 之前跑。** api 镜像的 CMD 先跑 `dist/db/migrate.js`，再 `exec`
> 起 `dist/index.js`（`apps/api/Dockerfile`），所以迁移在监听存在之前就自己跑完
> 了；等整栈起来之后再问，看到的只会是一片
> `applied`，下面这段 pre-flight 已经没有机会执行了。顺序见 §4。
>
> **`DATABASE_URL` 必须像上面那样单次传给它。** 自管 compose 栈的 `.env` 里没有
> 这一条（v2.5.0 手册里那条 ⚠️「不要顺手把 `.env` 里的 `DATABASE_URL` 取消注释。」
> 要求它保持注释状态，**不要为了跑通这条命令去取消**），
> 而同一份 `.env` 里的 `NODE_ENV=production` 会让 `env.ts` 在连库之前就拒掉默认的
> `postgres:postgres`，报「DATABASE_URL still uses the shipped postgres:postgres
> credential pair」——ledger 一行都读不到。这和 `db:backup` / `db:restore` /
> `kb:prune` 用的是同一种写法（同一条 ⚠️ 里的「需要 localhost 形态就单次传给它们」、
> `.env.example` 里 `DATABASE_URL` 那段）。数据库是托管实例、`.env` 里本来就写着
> `DATABASE_URL` 时，不加前缀。
>
> `127.0.0.1:5432` 是 compose 发布 postgres 的默认地址（`POSTGRES_HOST` /
> `POSTGRES_PORT` 改过就按改过的写），所以跑它的时候 postgres 容器得是起着的——
> 升级既有环境时，旧栈还在跑的那个窗口就是它。

它报 `applied / pending / drifted / orphan` 四态。两件事要现在就分清：

- **`orphan` 行必须处理，而且必须在迁移跑起来之前处理完**，但只有 `*_down.sql`
  结尾的那种会让命令非零退出。别的 orphan（forward 迁移被 rebase 删掉、或者改过
  名字留下的）只往 stdout 打一行 `orphan`，退出码仍然是 0。**这几行要自己看，不能
  只看退出码。** 见 v2.5.0 §2.1 的 pre-flight。
- **`drifted` 不拦截**：`migrate.ts` 的 `checksumOf` 注释写了为什么——改注释和改
  语义它分不出来，所以只报告。自 v2.5.0 起 `db/migrations/` 下**被改动过**的文件
  （`--diff-filter=M` 不能省：不加它，021–027 那批新增文件也会一起列出来，而这一
  段只关心被改过的那些）：

  ```bash
  git diff --stat --diff-filter=M v2.5.0 HEAD -- db/migrations/
  ```

  本次它列出的是：`018_measurement_cohort_index.sql` 只加了注释，说明它已被 025 取代；
  `015_function_test_unit_constraint_down.sql` 把一处 `RAISE NOTICE` 提成了
  `RAISE WARNING`，只影响回滚时那行日志的级别。
  **只有 018 会出现在 `drifted` 里**——校验和只对 `listMigrationFiles` 列出的文件
  算，而它按后缀把 `_down.sql` 挡在外面，所以 015 那处改动在这个报告里得不到任何
  判定。这不等于 `_down.sql` 进不了 ledger：进得了，上面那条 `orphan` pre-flight
  找的正是这种行——`printStatus` 把 `_down.sql` 结尾的 orphan 单独挑出来，往 stderr
  写「This database ran those \_down.sql files as forward migrations」，并让命令
  非零退出。**报出别的 `drifted` 行，说明你的库比 v2.5.0 还旧**，`git diff` 那个
  文件自己判断，不要套用这一段。

下面这张表覆盖 021–027。你的库里已经是 `applied` 的行跳过就行；`pending` 的按
顺序跑。

| 迁移 | 做什么                                                                                                      | `_down` 做什么（不是「建表」，是回滚）                                                                                                                                                                                         |
| ---- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 021  | 建 `passport_share_links`                                                                                   | ⚠️ `DROP TABLE` —— 患者铸出去的分享链接全没                                                                                                                                                                                    |

**026 里有一段探针会让整条迁移链失败**：它建一张 `LIKE app_users INCLUDING CONSTRAINTS`
的临时表，往里试插 `role = 'admin'`，被 CHECK 拒绝就 `RAISE EXCEPTION`（异常信息里
带着该跑哪条 `pg_constraint` 查询）。011 建的 `app_users_role_check` 本来就允许
`'admin'`，所以健康的库过得去。**过不去只说明一件事：这个库的 `app_users` 上挂着一
条拒绝 `'admin'` 的 CHECK。** 探针不认约束名，只认插不插得进去，所以约束被改窄、或
者被换成另一个名字的窄约束，它都拦得住。

**它拦不住的是相反那种库。** 约束整条被删掉的库照样过——无约束的列同样接受
`'admin'`，026 的头注释写明这是正确行为：探针断言的是「grant 不会被拒」，不是「约束
存在」。而 `011_status_check_constraints_down.sql` 干的正是把
`app_users_role_check` 删掉，所以被它跑过的库要靠上面那条 `orphan` pre-flight 发现，
这段探针发现不了。

**迁移现在随 api 容器启动跑**，所以它失败的表现是 api 起不来，原因在
`docker compose --profile prod logs api`。

**025 是本批唯一一条 `DROP INDEX` 在前的迁移，而且它锁读。** runner 把每个文件包在
一个事务里，`DROP` 拿到的 `ACCESS EXCLUSIVE` 会持有到 COMMIT，所以后面的 `CREATE`
是在这把锁下建的——`SELECT` 和写入一起挡（018 只挡写）。文件头的 LOCK NOTE 里有 dev
上的实测（233 行时 DROP+CREATE 合计约 6 ms，涨的是 CREATE 那半），以及一个数据量大
到这个窗口要紧时**替换掉 025**、而不是抢在它前面的 CONCURRENTLY 换法。

**回滚必须严格倒序，runner 会拦你。** ledger 里还有比目标号大的 forward 行时，
`migrate --down <id>` 直接报错退出（`_laterMigrationsStillApplied`），正常路径下跳
不了号。`--force` 的作用就是**跳过这道检查**：在 021–027 都已应用的库上
`--down 018 --force` 会照跑 018 的 `_down`（`DROP INDEX IF EXISTS idx_patient_measurements_cohort`），
把 025 建的那个索引删掉，然后只删 018 那一行 ledger——`--status` 继续报
`applied 025_…`，索引却已经不存在，而下一次 roll-forward 也不会重建它（runner 只按
文件名跳过）。要退到 025 之前，从最高号开始一条一条 `--down`。

**回滚跨过 021–024 就是永久丢数据**，具体见上表 021–024 那几行。这些是患者自己录
进去的东西，不是可以重算的派生数据。回滚前先按 v2.5.0 §1.7 做一次备份，并且**确认
那次备份真的落盘了**（`ls -l` 看大小，不要只看命令退出码）。

**回滚 026 或 027 丢的不是患者数据，但一样重跑不回来**：抓取历史只在
`trial_fetch_runs` 里，`trials:refresh` 补得回名单，补不回名单以外的东西。两个
`_down` 文件给的是同一条先导出的命令，跑它们之前也要跑：

```bash
# `$DATABASE_URL` 在自管 compose 栈的宿主机上是空的（§1.1），先给它一个值
export DATABASE_URL=postgres://<角色>:<密码>@127.0.0.1:5432/fshd_openrd
pg_dump --data-only --table=trial_fetch_runs "$DATABASE_URL" > runs.sql
```

### 1.2 ⛔ 反代要放行 `/s/*`，否则分享链接 404

临床护照的分享页挂在 `/s/passport/:token`，**在 `/api` 之外**。v2.5.0 的 Caddy
配置只有 `handle /api/*` 和一个 catch-all 到前端静态站，所以这个路径会被前端
路由接走：nginx 的 `try_files` 用 index.html 应答 **200**，expo-router 找不到这条
路由，渲染 `apps/mobile/app/+not-found.tsx`——医生看到的是「404 / 页面未找到 /
抱歉！您访问的页面不存在，当前页面功能待完善。」，而 HTTP 状态是 200。分享行照样
铸出来，`opened_count` 停在 0，患者的撤销列表于是告诉他医生从没打开过。

**反过来，「这个链接打不开了」是 API 自己的失效页**（`passport-share.routes.ts` 的
`RESOLVE_FAILED_PAGE`，由 `sendUnavailable` 以 404 送出）。看到它说明请求确实到了
API、反代是对的。**但它不告诉你这条链接出了什么事**——同一张页面也答给从来不存在的
token（冒烟测试探的就是这一种）、答给档案在打开途中被删掉的链接、答给 `/s/passport`
下任何没匹配上路由的 URL。这是故意的：分开答就等于告诉猜 token 的人哪一个猜中了。

本次仓库里的 `Caddyfile` 和 `apps/mobile/nginx.conf` 都已加好，但**生产机上的
Caddyfile 如果是手工维护的副本，要自己同步这一段**：

```
handle /s/* {
    reverse_proxy api:4000
}
```

放在 catch-all 之前。nginx 那份对应 `location /s/ { proxy_pass http://api:4000/s/; }`。

**改完 Caddyfile 必须让 caddy 真的重新读一遍，`up -d` 不会。** caddy 用的是拉取的
`caddy:2-alpine`，它的 image 和 service 定义这次都没动过（`git diff v2.5.0 HEAD -- docker-compose.yml`
里没有 caddy 段），compose 因此判定这个容器是最新的、原地不动；而 Caddyfile 是
`./Caddyfile:/etc/caddy/Caddyfile:ro` 这样的只读 bind mount，不会因为你在宿主机上
checkout 了新文件就自动生效。**照 §4 走完却漏掉这一步的结果是：磁盘上是新配置，
线上还是旧路由，患者继续拿到前端那张 200 的「页面未找到」。** 重建它：

```bash
docker compose --profile prod up -d --force-recreate caddy
```

重建而不是 `caddy reload`：重建之后容器里那份一定是宿主机上现在的这个文件。这一步
之后立刻确认反代真的起来了（`docker compose --profile prod ps caddy`，再跑 §4 的
冒烟测试）——配置写坏时受影响的是整站，不只是 `/s/`。

验证（`scripts/smoke-test.sh` 里也有这条）：一个不存在的 token 必须返回 **404，
且正文里有「这个链接打不开了」**。返回 200（正文是「页面未找到」）说明请求被前端
接走了，配置没生效——这条正是因为 200 和 404 在这里长得都像「正常」才写成断言的。

### 1.3 生产镜像新增一个文件

`apps/api/Dockerfile` 现在会 `COPY scripts/admin-role.mjs`。原因见 §3.1：

## 2. 定时任务：试验数据刷新（新增，要在宿主机配）

刷新**不在**请求路径上，也**不在** compose 里。它是宿主机 cron。不配它，
`trial_records` 会一直停在你导入时的那一份，患者看到的 `fetched_at` 会越来越旧
（页面会如实显示这个时间，不会假装是新的）。

生产镜像里没有 `tsx`（`npm ci --omit=dev`），所以 **`npm run trials:refresh` 在
生产上跑不了**。跑编译产物：

```bash
17 * * * * cd /srv/openrd && flock -n /tmp/openrd-trials.lock docker compose exec -T api node dist/modules/trials/refresh.cli.js >> /var/log/openrd/trials.log 2>&1
```

- `flock` 是为了慢抓取不与下一次重叠。
- **注意这条把 stderr 重定向进了日志文件，所以 cron 不会发邮件。** 失败的完整原因
  在 `/var/log/openrd/trials.log`。`trial_fetch_runs.error` 是同一句话在库里的副本，
  给以后从 psql 里翻的人看：只有超过 `MAX_RUN_ERROR_CHARS`（2000 字，
  `trials.repository.ts`）才截断并在末尾标出来，抓取器自己那种一行的失败信息两边
  是同一个字符串。但**不保证每次失败都有这一行**——run 行还没写成就挂掉，或者写
  失败原因这一步本身失败（`refresh.ts` 记 `Could not record why a refresh failed`），
  库里就什么都没有。**以日志为准。** 要靠邮件告警就去掉 `2>&1` 那段重定向，自己决定。
- 退出码只有在**每个**源都成功时才是 0。部分成功退出 1。
- 第一次手动跑一遍再进 cron，确认出站网络能到 clinicaltrials.gov。

**国内注册库（chinadrugtrials.org.cn）当前返回 0 条 FSHD 试验，这是注册库自己的
答案，不是抓取失败。** 它对第一次请求返回 202（反爬），随后 200 + 共 0 条记录。
数据里这两种情况是分开记的——027 的 `trial_fetch_runs.source_reported_total`：
抓取成功而这一列是 0，就是注册库自己说没有。**但页面不会把「注册库说 0 条」说
出来**：`TrialSourceStatus`（`apps/mobile/lib/trials.ts`）不带这一列，客户端拿不到
它（§7 说的就是这件事）。页面能分的只有「这次没取到」和「取到了，但列表里没有国内
的记录」，后者写成的是「本列表来自 ClinicalTrials.gov，不含仅在国内登记的试验」——
它不替注册库说话。所以「0 条是注册库的答案，还是我们没抓着」只能在库里问：

```sql
SELECT source, started_at, ok, source_reported_total, records_upserted, error
FROM trial_fetch_runs ORDER BY started_at DESC LIMIT 10;
```

## 3. 管理员账号

### 3.1 第一个管理员怎么来

角色不能自助获取：注册接口的枚举里没有 `admin`，没有任何 API 能提升自己。只能从
运维侧给：

```bash
docker compose exec api node /app/scripts/admin-role.mjs grant <phone>
```

- **是 `exec`，不是 `exec -T`。** 脚本要在终端上读一次确认；`-T` 拿掉终端后它会
  在开事务之前就拒绝执行，什么都不改。
- 账号必须**已经注册过**。脚本不建账号。
- **手机号写裸号（`13922220001`），不要带 `+86`。** `resolveAccount` 查的是
  「你输入的」和「`+86` + 你输入的」两种形态，所以裸号两种都能命中；写成
  `+8613922220001` 就只查这一种，而这一列历史上两种形态都存过。（真有两个账号
  分别以两种形态存在时，脚本会报 `2 accounts match` 并拒绝动手，不会替你挑一个。）
- 角色变更和 `audit_logs` 行在同一个事务里写。

撤销是 `revoke`。**撤销立即生效**——角色是每个请求现查数据库的，不是从 token 里
读的，所以不用等对方的登录态过期。

### 3.2 上线后要核对的一件事

```sql
SELECT id, phone_number, role FROM app_users WHERE role = 'admin';
```

这张表应该只有你自己刚授的那些。如果有意料之外的行，先 revoke 再查
`audit_logs`（`event_type` 上本次新加了复合索引，查得动）。

### 3.3 审计表会长

`audit_logs` 现在也记**读**——管理员看一次患者档案就是一行。这是设计，不是冗余：
在这个后台里，「谁看了谁」才是要紧的事件。026 给 `(event_type, occurred_at)` 建了
复合索引。留存期 180 天，清理逻辑沿用既有的 purge。

## 4. 上线顺序（相对 v2.5.0 §3.2 的差异）

v2.5.0 §3.2 的顺序照旧，插入下面这几步。**先做迁移 pre-flight，再拉栈**——api
容器的 CMD 自己会跑迁移（§1.1），栈起来之后再问库就已经晚了。

1. 备份（**确认落盘**，见 §1.1）
2. `git checkout` + `.env` 补齐（v2.5.0 §1.0-0 那个顺序陷阱仍然成立）
3. **迁移 pre-flight（趁旧栈还跑着，在宿主机上）**：`npm run db:migrate:status`，
   **带上 §1.1 那个 `DATABASE_URL=…` 前缀**。`orphan` 行必须在这里处理掉
   （v2.5.0 §2.1；退出码不替你看这几行，见 §1.1），并记下你的库停在哪一条（§1.1）
4. **同步反代的 `/s/*` 段**（§1.2）
5. `docker compose --profile prod build`（**必须 build，见 §1.3**）
6. `docker compose --profile prod up -d` —— **`--profile prod` 不能省**：caddy 是
   `profiles: ['prod']`，minio 是 `profiles: ['minio', 'prod']`，裸 `docker compose up -d`
   既不起反代也不起对象存储。迁移在这一步随 api 容器跑完，**不用再手工
   `npm run db:migrate`**（v2.5.0 §3.2 step 4 已经写了这件事；两条路径共用一把
   advisory lock，所以撞上也不会互相踩）。api 起不来时，迁移的输出在
   `docker compose --profile prod logs api` 里
7. **重建 caddy 让新 Caddyfile 生效**（§1.2）：
   `docker compose --profile prod up -d --force-recreate caddy`
8. `npm run db:migrate:status` 复核（**同样带 §1.1 那个前缀**）：021–027 应该全是
   `applied`（`drifted` 见 §1.1）
9. `docker compose exec api node /app/scripts/admin-role.mjs grant <你自己的手机号>`
   （裸号，且是 `exec` 不是 `exec -T`，见 §3.1）
10. **配 cron（§2），并手动跑一次**
11. 冒烟测试 `scripts/smoke-test.sh`（含 `/s/` 那条断言——相对上一次部署是新的，
    它同时也是第 7 步生效了没有的验证）

## 5. 上线后第一件会发生的事：所有人看到同意页

隐私政策版本 bump 了，所以**每个活跃账号下次打开 App 都会先进一屏「有条款需要你
确认」**。这是隐私政策 §9 承诺过的，不是故障。

盯这几件事：

- 客服/群里会收到「怎么突然要我同意」的问题。同意页第一屏就写了变了什么
  （管理员可以查阅和代填档案），可以直接引用那几句。
- **Web export 和 API 是分开发布的。** 如果只更新了 API 而前端还是旧 bundle，
  服务端会说「有个版本要确认」而旧 bundle 显示不出来。这个死循环代码里挡掉了
  （存的同意版本等于当前 bundle 版本时跳过），但**正确的做法仍然是两个一起发**。
- 点「暂不同意」的人不会被踢出去，也不会被限制功能——见 §0 最后那段。
