## 0. 这次发了什么

三块新东西，外加一批修正。

1. **临床试验数据是活的了。** `trial_records` 由定时任务从 ClinicalTrials.gov
   刷新，不在请求路径上。问答层不再只能从建库时的语料回答「有没有在招的试验」。
2. **管理员后台。** 患者名单、单个患者的档案（账号、身份、基线，以及报告 / 随访 /
   跌倒 / 量表这几段历史）、单人导出与全量 CSV 导出，外加只读的运维视图
   （`/ops/corpus`、`/ops/parse-failures`、`/ops/ai-usage`、`/ops/health`）。
   **改患者档案只有一条路**：`PUT /patients/:userId/baseline`（另一个非 GET 是
   `POST /exports/patients.csv`，它是导出，不写任何患者数据），而且只认
   `ADMIN_WRITABLE_BASELINE_FIELDS` 这张白名单上的字段，改到清单外的字段返回 400
   并把这次被拒的字段逐个点名。白名单上是身份与病史——姓名、称呼、所在地区、出生
   年份、确诊年份、家族史、起病部位、备注；**FSHD 分型、D4Z4 重复数、单倍型、甲基化不在上面**，
   后台里那几栏只读，服务端也会拒绝——**连清空也算改动，一样被拒**。这限制的是谁能
   打字，不是这几项的值从哪来：它们从患者上传的文件里读出来——本平台认定其中一份作为
   这份档案的基因证据，那一份**不一定是化验所出的基因报告**（转抄了重复数的病历摘要
   一样会被认定，括号里写的也不是「报告读取」，见 §3.4）；分型和 D4Z4 另外还在患者的
   「编辑资料」里有框，这几项在报告详情页的修正表单上都有框。患者问
   「这项写错了怎么办」，**先看 §3.4 再开口**——那一节的重点是哪些话能说、哪些话你
   其实不知道。读也审计。角色不能自助获取。
3. **重新征求同意。** 隐私政策因为第 2 条实质变更，版本号已 bump——**上线后每个
   活跃账号下次打开都会先看到一屏同意页**。这不是 bug，见 §5。

还有一件事本次**没有**做，运维需要知道：**患者点「暂不同意」并不会阻止管理员读他的
档案。** API 里没有任何地方把管理员访问和这个同意台账挂钩。同意页没有声称它能挡住
（有测试钉着那句话不许出现），但这是个待法务确认的问题，不是已经解决的问题。

## 1. 相对 v2.5.0 的破坏性变化

### 1.1 ⛔ 数据库要从 020 一路跑到 027；021–024 的回滚会永久删患者数据

v2.5.0 手册的 §2.1 标题写的是「数据库迁移（013 → 020）」，仓库里现在有到 **027**。

**这份手册不知道你的生产库停在哪一条**，也不要去猜——上一版手册写到 020 只说明
写它的时候仓库里最新是 020，不说明生产库现在就在 020。先问库自己（在宿主机上跑）：

```bash
DATABASE_URL=postgres://<角色>:<密码>@127.0.0.1:5432/fshd_openrd npm run db:migrate:status
```

> 这条走 `tsx`，是 devDependency。**宿主机必须是完整 `npm ci`，不能是 `--omit=dev`。**
> 生产镜像里没有 tsx，所以这条不能在容器里用 `npm run` 跑。
>
> **必须在 `up -d` 之前跑。** api 镜像的 CMD 先跑 `dist/db/migrate.js`，再 `exec`
> 起 `dist/index.js`（`apps/api/Dockerfile`），所以迁移在监听存在之前就自己跑完
> 了；等整栈起来之后再问，看到的只会是一片
> `applied`，下面这段 pre-flight 已经没有机会执行了。顺序见 §4。
>
> **`DATABASE_URL` 必须像上面那样单次传给它。** 自管 compose 栈的 `.env` 里没有
> 这一条（v2.5.0 手册里那条 ⚠️「不要顺手把 `.env` 里的 `DATABASE_URL` 取消注释。」
> 要求它保持注释状态，**不要为了跑通这条命令去取消**），
> 而同一份 `.env` 里的 `NODE_ENV=production` 会让 `env.ts` 在连库之前就拒掉默认的
> `postgres:postgres`，报「DATABASE_URL still uses the shipped postgres:postgres
> credential pair」——ledger 一行都读不到。这和 `db:backup` / `db:restore` /
> `kb:prune` 用的是同一种写法（同一条 ⚠️ 里的「需要 localhost 形态就单次传给它们」、
> `.env.example` 里 `DATABASE_URL` 那段）。数据库是托管实例、`.env` 里本来就写着
> `DATABASE_URL` 时，不加前缀。
>
> `127.0.0.1:5432` 是 compose 发布 postgres 的默认地址（`POSTGRES_HOST` /
> `POSTGRES_PORT` 改过就按改过的写），所以跑它的时候 postgres 容器得是起着的——
> 升级既有环境时，旧栈还在跑的那个窗口就是它。

它报 `applied / pending / drifted / orphan` 四态。两件事要现在就分清：

- **`orphan` 行必须处理，而且必须在迁移跑起来之前处理完**，但只有 `*_down.sql`
  结尾的那种会让命令非零退出。别的 orphan（forward 迁移被 rebase 删掉、或者改过
  名字留下的）只往 stdout 打一行 `orphan`，退出码仍然是 0。**这几行要自己看，不能
  只看退出码。** 见 v2.5.0 §2.1 的 pre-flight。
- **`drifted` 不拦截**：`migrate.ts` 的 `checksumOf` 注释写了为什么——改注释和改
  语义它分不出来，所以只报告。自 v2.5.0 起 `db/migrations/` 下**被改动过**的文件
  （`--diff-filter=M` 不能省：不加它，021–027 那批新增文件也会一起列出来，而这一
  段只关心被改过的那些）：

  ```bash
  git diff --stat --diff-filter=M v2.5.0 HEAD -- db/migrations/
  ```

  本次它列出的是：`018_measurement_cohort_index.sql` 只加了注释，说明它已被 025 取代；
  `015_function_test_unit_constraint_down.sql` 把一处 `RAISE NOTICE` 提成了
  `RAISE WARNING`，只影响回滚时那行日志的级别。
  **只有 018 会出现在 `drifted` 里**——校验和只对 `listMigrationFiles` 列出的文件
  算，而它按后缀把 `_down.sql` 挡在外面，所以 015 那处改动在这个报告里得不到任何
  判定。这不等于 `_down.sql` 进不了 ledger：进得了，上面那条 `orphan` pre-flight
  找的正是这种行——`printStatus` 把 `_down.sql` 结尾的 orphan 单独挑出来，往 stderr
  写「This database ran those \_down.sql files as forward migrations」，并让命令
  非零退出。**报出别的 `drifted` 行，说明你的库比 v2.5.0 还旧**，`git diff` 那个
  文件自己判断，不要套用这一段。

下面这张表覆盖 021–027。你的库里已经是 `applied` 的行跳过就行；`pending` 的按
顺序跑。

| 迁移 | 做什么                                                                                                      | `_down` 做什么（不是「建表」，是回滚）                                                                                                                                                                                         |
| ---- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 021  | 建 `passport_share_links`                                                                                   | ⚠️ `DROP TABLE` —— 患者铸出去的分享链接全没                                                                                                                                                                                    |
| 022  | 建 `instruments` / `instrument_administrations` / `instrument_item_responses`，加 CHECK 与不可变触发器      | ⚠️ `DROP TABLE` 那三张表（量表作答），**并且改写 `patient_profiles`**：把 `independentlyAmbulatory` 折回布尔，`'unable'` 和 `'assisted'` 一起变成 `false`，这个区分从库里找不回来——文件自己 `RAISE WARNING` 报数               |
| 023  | 建 `patient_falls`                                                                                          | ⚠️ `DROP TABLE` —— 没有随访 twin 的跌倒记录整条消失（`_down` 会先 `RAISE WARNING` 报有多少条）                                                                                                                                 |
| 024  | 建 `passport_pickup_codes`                                                                                  | ⚠️ `DROP TABLE` —— 取件码全没                                                                                                                                                                                                  |
| 025  | 重建 `idx_patient_measurements_cohort`（`muscle_group, profile_id, recorded_at DESC, strength_score DESC`） | 删掉它并重建回 018 的 `(muscle_group, strength_score)`；见下                                                                                                                                                                   |
| 026  | 建 `trial_records` / `trial_fetch_runs` + `audit_logs (event_type, occurred_at)` 复合索引                   | ⚠️ 删这两张表和那个索引。`trial_records` 是缓存，一次 `trials:refresh` 就回来；**`trial_fetch_runs` 回不来**——它是「什么时候能、什么时候不能抓到各个源」的唯一记录，删掉之后「上次成功抓取是什么时候」在下一次成功之前没有答案 |
| 027  | `trial_fetch_runs` 加 `source_reported_total` 一列 + 两条 CHECK                                             | ⚠️ 删掉那一列和那两条 CHECK。**已记下的 `source_reported_total` 重抓不回来**：那个数属于读到它的那一刻，重抓答的是今天                                                                                                         |

**026 里有一段探针会让整条迁移链失败**：它建一张 `LIKE app_users INCLUDING CONSTRAINTS`
的临时表，往里试插 `role = 'admin'`，被 CHECK 拒绝就 `RAISE EXCEPTION`（异常信息里
带着该跑哪条 `pg_constraint` 查询）。011 建的 `app_users_role_check` 本来就允许
`'admin'`，所以健康的库过得去。**过不去只说明一件事：这个库的 `app_users` 上挂着一
条拒绝 `'admin'` 的 CHECK。** 探针不认约束名，只认插不插得进去，所以约束被改窄、或
者被换成另一个名字的窄约束，它都拦得住。

**它拦不住的是相反那种库。** 约束整条被删掉的库照样过——无约束的列同样接受
`'admin'`，026 的头注释写明这是正确行为：探针断言的是「grant 不会被拒」，不是「约束
存在」。而 `011_status_check_constraints_down.sql` 干的正是把
`app_users_role_check` 删掉，所以被它跑过的库要靠上面那条 `orphan` pre-flight 发现，
这段探针发现不了。

**迁移现在随 api 容器启动跑**，所以它失败的表现是 api 起不来，原因在
`docker compose --profile prod logs api`。

**025 是本批唯一一条 `DROP INDEX` 在前的迁移，而且它锁读。** runner 把每个文件包在
一个事务里，`DROP` 拿到的 `ACCESS EXCLUSIVE` 会持有到 COMMIT，所以后面的 `CREATE`
是在这把锁下建的——`SELECT` 和写入一起挡（018 只挡写）。文件头的 LOCK NOTE 里有 dev
上的实测（233 行时 DROP+CREATE 合计约 6 ms，涨的是 CREATE 那半），以及一个数据量大
到这个窗口要紧时**替换掉 025**、而不是抢在它前面的 CONCURRENTLY 换法。

**回滚必须严格倒序，runner 会拦你。** ledger 里还有比目标号大的 forward 行时，
`migrate --down <id>` 直接报错退出（`_laterMigrationsStillApplied`），正常路径下跳
不了号。`--force` 的作用就是**跳过这道检查**：在 021–027 都已应用的库上
`--down 018 --force` 会照跑 018 的 `_down`（`DROP INDEX IF EXISTS idx_patient_measurements_cohort`），
把 025 建的那个索引删掉，然后只删 018 那一行 ledger——`--status` 于是同时报
`pending 018_…` 和 `applied 025_…`。

**下一次 roll-forward 会把这个索引建回来，但建成 018 的形状。**
`applyPendingMigrations` 是按 ledger 行跳过的（`applied.has(file)`，key 就是
`schema_migrations` 里那一行），而 `--force` 删掉的正是 018 那一行，所以 018 恰恰是
不被跳过的那个文件。触发 roll-forward 的是 api 容器的创建——CMD 先跑
`dist/db/migrate.js`（见上），所以 §4 第 6 步的 `up -d` 会带着它一起跑。之后索引以同一个
名字回到库里，定义却是 018 的 `(muscle_group, strength_score)`，而不是 025 的
`(muscle_group, profile_id, recorded_at DESC, strength_score DESC)`；`--status` 把
018 和 025 一起报成 `applied`、退出 0，连上面 pre-flight 让你留意的那行
`drifted  018_…` 都跟着消失了——018 是被这一次 roll-forward 重新记进 ledger 的，
记的是磁盘上这个文件的校验和。所以 §4 第 8 步看不出任何异常，而手动 `CREATE INDEX`
只会撞 42P07「already exists」。「和其他患者比」背后那条查询于是安静地跑在 018 的索
引上，而 025 存在的理由就是它不该跑在那上面。

**索引在不在判断不了这件事——018 的形状和 025 的形状顶着同一个名字。** 要看的是列。
下面这条把列和 ledger 一起答了：

```bash
# `$DATABASE_URL` 在自管 compose 栈的宿主机上是空的（§1.1），先给它一个值
export DATABASE_URL=postgres://<角色>:<密码>@127.0.0.1:5432/fshd_openrd
psql "$DATABASE_URL" -c "
SELECT CASE
         WHEN d IS NULL THEN 'MISSING'
         WHEN d LIKE '%(muscle_group, profile_id, recorded_at DESC, strength_score DESC)' THEN '025'
         WHEN d LIKE '%(muscle_group, strength_score)' THEN '018'
         ELSE 'OTHER: ' || d
       END AS index_shape,
       (SELECT count(*) FROM schema_migrations
         WHERE id = '025_measurement_cohort_index_per_patient.sql') AS ledger_025
  FROM (SELECT pg_get_indexdef(to_regclass('public.idx_patient_measurements_cohort')) AS d) t;"
```

| `index_shape` | `ledger_025` | 这个库在哪                                                            |
| ------------- | ------------ | --------------------------------------------------------------------- |
| `025`         | `1`          | 正常，下面的修法不用做                                                |
| `018`         | `1`          | 本段说的那个状态：ledger 说 025 应用过，索引却是 018 的形状           |
| `018`         | `0`          | 下面第一半做了、第二半没做：ledger 行删了，roll-forward 还没跑        |
| `MISSING`     | `1` 或 `0`   | 索引不在：`--down 018 --force` 跑过，之后还没有任何 roll-forward 接上 |

**修法有两半，只做第一半的库停在 `018` / `0`。**

**第一半：把 025 那一行 ledger 删掉**，让 roll-forward 连 025 一起重跑——025 的正文
开头就是 `DROP INDEX IF EXISTS`，重跑时它先删掉 018 建的那个再建自己的：

```bash
psql "$DATABASE_URL" -c "DELETE FROM schema_migrations WHERE id = '025_measurement_cohort_index_per_patient.sql';"
```

**第二半：让 roll-forward 真的发生。** 删 ledger 行不碰 schema，而迁移只在 api 容器
启动时跑那一次（CMD 先 `dist/db/migrate.js`，再 `exec` 起服务），所以这一半怎么做取决
于栈起没起：

- **还没走到 §4 第 6 步**：删完就够了，第 6 步的 `up -d` 建 api 容器时会连 025 一起
  补上。
- **栈已经在跑**：**再敲一次 `docker compose --profile prod up -d` 什么都不会发生**
  ——镜像和 compose 配置没变时它只把容器报成 `Running`，容器不重建，CMD 也就不重跑。
  两条路二选一：

  ```bash
  # 一、在宿主机的仓库根目录跑，api 不中断。写法和 §1.1 那条 pre-flight 一样，
  #     同样要求宿主机是完整 `npm ci`（tsx 是 devDependency）。必须在仓库根目录，
  #     `db:migrate` 是根 package.json 的脚本
  DATABASE_URL=postgres://<角色>:<密码>@127.0.0.1:5432/fshd_openrd npm run db:migrate

  # 二、重建 api 容器，让它自己的 CMD 跑；api 会断一下
  docker compose --profile prod up -d --force-recreate api
  ```

  差别不只是中断：第一条是在 api 还在读表的时候跑 025 的 `DROP`+`CREATE`，那对语句
  持 `ACCESS EXCLUSIVE` 到 COMMIT，`SELECT` 一起挡（见上）；第二条先停旧容器再迁移，
  正是 025 的 LOCK NOTE 判断这个窗口可接受时假设的那个「没有并发读写」的形状。

两半都做完，再跑一遍上面那条检查，要答 `025` / `1`。

要**真的**退到 025 之前（而不是修上面这个状态），从最高号开始一条一条 `--down`；那
会连 026/027 一起回滚，见下面讲它们的那段。

**回滚跨过 021–024 就是永久丢数据**，具体见上表 021–024 那几行。这些是患者自己录
进去的东西，不是可以重算的派生数据。回滚前先按 v2.5.0 §1.7 做一次备份，并且**确认
那次备份真的落盘了**（`ls -l` 看大小，不要只看命令退出码）。

**回滚 026 或 027 丢的不是患者数据，但一样重跑不回来**：抓取历史只在
`trial_fetch_runs` 里，`trials:refresh` 补得回名单，补不回名单以外的东西。两个
`_down` 文件给的是同一条先导出的命令，跑它们之前也要跑：

```bash
# `$DATABASE_URL` 在自管 compose 栈的宿主机上是空的（§1.1），先给它一个值
export DATABASE_URL=postgres://<角色>:<密码>@127.0.0.1:5432/fshd_openrd
pg_dump --data-only --table=trial_fetch_runs "$DATABASE_URL" > runs.sql
```

### 1.2 ⛔ 反代要放行 `/s/*`，否则分享链接 404

临床护照的分享页挂在 `/s/passport/:token`，**在 `/api` 之外**。v2.5.0 的 Caddy
配置只有 `handle /api/*` 和一个 catch-all 到前端静态站，所以这个路径会被前端
路由接走：nginx 的 `try_files` 用 index.html 应答 **200**，expo-router 找不到这条
路由，渲染 `apps/mobile/app/+not-found.tsx`——医生看到的是「404 / 页面未找到 /
抱歉！您访问的页面不存在，当前页面功能待完善。」，而 HTTP 状态是 200。分享行照样
铸出来，`opened_count` 停在 0，患者的撤销列表于是告诉他医生从没打开过。

**反过来，「这个链接打不开了」是 API 自己的失效页**（`passport-share.routes.ts` 的
`RESOLVE_FAILED_PAGE`，由 `sendUnavailable` 以 404 送出）。看到它说明请求确实到了
API、反代是对的。**但它不告诉你这条链接出了什么事**——同一张页面也答给从来不存在的
token（冒烟测试探的就是这一种）、答给档案在打开途中被删掉的链接、答给 `/s/passport`
下任何没匹配上路由的 URL。这是故意的：分开答就等于告诉猜 token 的人哪一个猜中了。

本次仓库里的 `Caddyfile` 和 `apps/mobile/nginx.conf` 都已加好，但**生产机上的
Caddyfile 如果是手工维护的副本，要自己同步这一段**：

```
handle /s/* {
    reverse_proxy api:4000
}
```

放在 catch-all 之前。nginx 那份对应 `location /s/ { proxy_pass http://api:4000/s/; }`。

**改完 Caddyfile 必须让 caddy 真的重新读一遍，`up -d` 不会。** caddy 用的是拉取的
`caddy:2-alpine`，它的 image 和 service 定义这次都没动过（`git diff v2.5.0 HEAD -- docker-compose.yml`
里没有 caddy 段），compose 因此判定这个容器是最新的、原地不动；而 Caddyfile 是
`./Caddyfile:/etc/caddy/Caddyfile:ro` 这样的只读 bind mount，不会因为你在宿主机上
checkout 了新文件就自动生效。**照 §4 走完却漏掉这一步的结果是：磁盘上是新配置，
线上还是旧路由，患者继续拿到前端那张 200 的「页面未找到」。** 重建它：

```bash
docker compose --profile prod up -d --force-recreate caddy
```

重建而不是 `caddy reload`：重建之后容器里那份一定是宿主机上现在的这个文件。这一步
之后立刻确认反代真的起来了（`docker compose --profile prod ps caddy`，再跑 §4 的
冒烟测试）——配置写坏时受影响的是整站，不只是 `/s/`。

验证（`scripts/smoke-test.sh` 里也有这条）：一个不存在的 token 必须返回 **404，
且正文里有「这个链接打不开了」**。返回 200（正文是「页面未找到」）说明请求被前端
接走了，配置没生效——这条正是因为 200 和 404 在这里长得都像「正常」才写成断言的。

### 1.3 生产镜像新增一个文件

`apps/api/Dockerfile` 现在会 `COPY scripts/admin-role.mjs`。原因见 §3.1：
第一个管理员必须在跑着的生产栈上产生，而在 psql 里手写 `UPDATE app_users` 会丢掉
脚本在同一事务里写的 `audit_logs` 行。

这意味着**必须重新 build 镜像**，不能只 `docker compose up -d` 拉旧镜像。

## 2. 定时任务：试验数据刷新（新增，要在宿主机配）

刷新**不在**请求路径上，也**不在** compose 里。它是宿主机 cron。不配它，
`trial_records` 会一直停在你导入时的那一份，患者看到的 `fetched_at` 会越来越旧
（页面会如实显示这个时间，不会假装是新的）。

生产镜像里没有 `tsx`（`npm ci --omit=dev`），所以 **`npm run trials:refresh` 在
生产上跑不了**。跑编译产物：

```bash
17 * * * * cd /srv/openrd && flock -n /tmp/openrd-trials.lock docker compose exec -T api node dist/modules/trials/refresh.cli.js >> /var/log/openrd/trials.log 2>&1
```

- `flock` 是为了慢抓取不与下一次重叠。
- **注意这条把 stderr 重定向进了日志文件，所以 cron 不会发邮件。** 失败的完整原因
  在 `/var/log/openrd/trials.log`。`trial_fetch_runs.error` 是同一句话在库里的副本，
  给以后从 psql 里翻的人看：只有超过 `MAX_RUN_ERROR_CHARS`（2000 字，
  `trials.repository.ts`）才截断并在末尾标出来，抓取器自己那种一行的失败信息两边
  是同一个字符串。但**不保证每次失败都有这一行**——run 行还没写成就挂掉，或者写
  失败原因这一步本身失败（`refresh.ts` 记 `Could not record why a refresh failed`），
  库里就什么都没有。**以日志为准。** 要靠邮件告警就去掉 `2>&1` 那段重定向，自己决定。
- 退出码只有在**每个**源都成功时才是 0。部分成功退出 1。
- 第一次手动跑一遍再进 cron，确认出站网络能到 clinicaltrials.gov。

**国内注册库（chinadrugtrials.org.cn）当前返回 0 条 FSHD 试验，这是注册库自己的
答案，不是抓取失败。** 它对第一次请求返回 202（反爬），随后 200 + 共 0 条记录。
数据里这两种情况是分开记的——027 的 `trial_fetch_runs.source_reported_total`：
抓取成功而这一列是 0，就是注册库自己说没有。

**但页面不会把「注册库说 0 条」说出来**：`TrialSourceStatus`
（`apps/mobile/lib/trials.ts`）不带这一列，客户端拿不到它（§7 说的就是这件事）。

页面能说的是国内那半边**在我们这边**跑成了什么样，而这个它分得很细：
`describeChinaCoverage` 按状态换句子，患者读到的是哪一句，能把库里的可能性收窄到
表里对应的那一格——**最后一行除外**，它把「请求还没回来」「请求失败」「响应里连这个
源的块都没有」并成同一句话，从患者那头分不开。

下面这张表是把这一页在每种状态下渲染出来、照抄屏幕上那一句得到的，值班时按患者
念给你的原话查。**抄的是每一句的开头**：后面还跟着什么，取决于屏幕上画没画得出名单，
见表下面几段。

| 患者屏幕上那一句                                                                                                                                                  | 库里对应的状态                                                                      |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 国内这部分还没有抓取过                                                                                                                                            | 这个源一条 `trial_fetch_runs` 都没有                                                |
| 国内这部分这次没有取到（上次成功抓取：…）                                                                                                                         | 最近一次 run `ok = false`，`finished_at` 有值                                       |
| 国内这部分最近一次抓取还没有返回结果（…）                                                                                                                         | 最近一次 run 有 `started_at`、`finished_at` 是空的（可能正在跑，也可能中途挂了）    |
| 国内这部分最近一次抓取（…）是成功的，但一条记录都没有取回来                                                                                                       | 最近一次 run `ok = true`，而 `trial_records` 里这个源没有行——**今天线上就是这一格** |
| 国内这部分来自药物临床试验登记与信息公示平台（抓取于 …）                                                                                                          | 这个源有行，最近一次 run 也是成功的                                                 |
| 同上，后面接「国内这部分最近一次抓取没有成功（上次成功抓取：…），此后有没有变过，这里看不出来」（run 没返回时这半句换成「国内这部分最近一次抓取还没有返回结果」） | 这个源有行，但最近一次 run 没成功：屏幕上那些行是上一次成功留下的                   |
| 本页现在没有来自国内登记平台的记录                                                                                                                                | 请求还没回来、请求失败，或者响应里连这个源的块都没有                                |

说「这边没有国内记录」的那几句，后面都跟着「国内登记的试验请直接查药物临床试验登记
与信息公示平台（chinadrugtrials.org.cn）」——表里最后那句固定话也带着它。

**中间那句「所以下面这份名单目前只有 ClinicalTrials.gov 的记录」不是这样。** 它挂在
说「这边没有国内记录」的那几句上，而且只在名单画得出来的时候挂：名单画不出来时
（一条都没有、读不出抓取时间、请求失败、还在加载）没有它，因为它说的是名单。

**表里最后那句固定话是例外：它虽然也在说这边没有国内记录，却在任何情况下都不带这
一句**——包括名单好端端画在下面的时候。这一句是在页面对国内那次抓取一无所知时说的：
它只说页面上现在没有什么，不替名单描述范围。所以值班时**别拿有没有中间那句去判断他
屏幕上有没有名单**，直接问他有没有「拉取于 …」那一行。

屏幕上真有国内记录的时候不指路，改成「请以 chinadrugtrials.org.cn 上的原始记录为准」。
**这句话是不是结尾要看那次抓取**：最近一次成功，它就是结尾；没成功或没返回，它后面还
接着表里「同上，后面接……」那一行写的那半句。

**没有一句是「本页只收录 ClinicalTrials.gov 的记录，不含仅在国内登记的试验」。**
上一版这里引的就是这一句，它已经不在代码里了：我们确实抓 chinadrugtrials.org.cn，
把「我们不收录」印在「我们抓了、注册库给了零条」上面，是拿本平台的缺席替注册库
回答。今天线上那一格里现在有一句「这不等于国内就没有相关的试验」，紧挨在指路那半句
前面。页面说到这里就不再往下走：零条究竟是注册库自己的答案，还是我们的抓取没认出来，
它一个字都不断。

**页面分不了的就是这最后一步：「零条是注册库自己的答案，还是我们的抓取没认出来」。**
`ok = true` 加空列表两种都成立，能分开它们的那一列没有上线到客户端。所以这个问题
只能在库里问：

```sql
SELECT source, started_at, ok, source_reported_total, records_upserted, error
FROM trial_fetch_runs ORDER BY started_at DESC LIMIT 10;
```

## 3. 管理员账号

### 3.1 第一个管理员怎么来

角色不能自助获取：注册接口的枚举里没有 `admin`，没有任何 API 能提升自己。只能从
运维侧给：

```bash
docker compose exec api node /app/scripts/admin-role.mjs grant <phone>
```

- **是 `exec`，不是 `exec -T`。** 脚本要在终端上读一次确认；`-T` 拿掉终端后它会
  在开事务之前就拒绝执行，什么都不改。
- 账号必须**已经注册过**。脚本不建账号。
- **手机号写裸号（`13922220001`），不要带 `+86`。** `resolveAccount` 查的是
  「你输入的」和「`+86` + 你输入的」两种形态，所以裸号两种都能命中；写成
  `+8613922220001` 就只查这一种，而这一列历史上两种形态都存过。（真有两个账号
  分别以两种形态存在时，脚本会报 `2 accounts match` 并拒绝动手，不会替你挑一个。）
- 角色变更和 `audit_logs` 行在同一个事务里写。

撤销是 `revoke`。**撤销立即生效**——角色是每个请求现查数据库的，不是从 token 里
读的，所以不用等对方的登录态过期。

**授予不对称：被授予的人如果当时已经登录着，要退出重新登录一次，后台入口才会出现。**
挡访问的和画入口的不是同一段东西。服务端确实现查数据库（`requireAdmin`），所以授予之
后他的请求立刻就能过；但 App 画不画「我的」里那一行，读的是 `AuthContext` 里的
`user.role`，而那是登录那一次的响应存在设备上的副本——`setSession` 只在登录/注册时写
它，没有任何地方会去刷新。所以他手机上原来那个登录态里：「我的」不会长出「后台」那一
行，直接在地址栏敲 `/p-admin` 也会被 `app/_layout.tsx` 的路由闸换回 `/p-home`——两处都
是画不画的决定，不是权限判断，`lib/admin-access.ts` 写了为什么允许它是旧的。**退出登录
再登进来就有了**：登录响应带回来的是新角色。

从没登录过的账号不受影响：它第一次登录拿到的就是授予之后的角色。

### 3.2 上线后要核对的一件事

```sql
SELECT id, phone_number, role FROM app_users WHERE role = 'admin';
```

这张表应该只有你自己刚授的那些。如果有意料之外的行，先 revoke 再查
`audit_logs`（`event_type` 上本次新加了复合索引，查得动）。

### 3.3 审计表会长

`audit_logs` 现在也记**读**——管理员看一次患者档案就是一行。这是设计，不是冗余：
在这个后台里，「谁看了谁」才是要紧的事件。026 给 `(event_type, occurred_at)` 建了
复合索引。留存期 180 天，清理逻辑沿用既有的 purge。

### 3.4 患者说基因那几项写错了，怎么答

**这一节给的是「去哪儿」，不是「怎么改」，这是有意的。** 上一版这里写了一套「让他打开
那份报告，点『识别有误？手动修正』，改完保存」的话术。那套话对一部分患者是对的，对另一
部分是空的：那个按钮只在报告的状态是 `parsed` 或 `needs_review` 时才画出来，报告还在
识别中、识别失败、或者刚上传还没跑，那一页上根本没有它，服务端也会拒（409）。

你这一页的「报告」列表里确实印着每份报告的状态，而且那**就是**判定用的那个字段——报告
详情页按它画那个按钮（`parsed` 和 `needs_review` 画，其余不画），服务端也按它收或拒。
但它**仍然不足以让你在电话里下结论**：印的是英文原始状态码，这一页上没有对照表；而且它
只是你打开这一页那一刻的快照，患者点一次「重新识别」，那一行立刻作废。**照着上一版念，
等于当着患者的面许一个你不知道能不能兑现的诺。**

能如实说的只有三件事。

**一、你改不动，这一条是确定的。** 后台没有分型、D4Z4 重复数、单倍型、甲基化的输入框，
服务端也会拒——改动其中任何一项返回 400，并把这次被拒的字段逐个点名（基因结果和「患者
对自己身体的回答」分成两句，理由不一样），**连清空也算改动**。所以不要答应「你告诉我，
我帮你改」，也不要绕到数据库里去改。

**二、值是多少、值旁边那几个字是什么意思，可以照着解释。** 来源跟着值走，但**印法随他
手上是哪一份而不同**：分享给医生的那一页上是跟在值后面的括号（「6（报告读取）」），他
自己手机上的临床护照和导出的 PDF 上是值**下面**单独的一小行，没有括号。所以别问「括号
里写的是什么」，问「那个数字旁边或下面还写了几个字吗，念给我听」。**有的值下面确实什么
都没有**，那不是他没找到。**你这一页上没有这套词**：后台每个字段后面挂的是「无代填记录 /
管理员代填 / 来源不明」，那是另一套词，说的也是另一件事（有没有代填记录，不是值从哪
来）。**来源只说这个值是从哪来的，不说该去哪儿改；不要把它当路标念。**

先弄清他念的是哪一行。**带自己来源的是这几行**：手机和 PDF 上写作「基因类型 / D4Z4
重复数 / 甲基化值 / 诊断日期」，医生那一页上第一行叫「分型」、第三行叫「甲基化」，是同
样几行（下面按医生那一页的叫法写）。**单倍型没有自己的来源**——它拼在「基因证据」那一
行里（手机上这一块的标题随情况写「证据摘要」或「诊断信息」），那一行的来源说的是整行。
**「诊断进度」那一格不在这几行里**：它是他自己在建档表单上选的那句话，来源写在标题上
（「本人填写的诊断进度」/「管理员代填的诊断进度」/「来源不明的诊断进度」），**下面这张
表不适用于它**——他念的如果是那一格，先说清楚那是他自己选的一句话，不是化验结果。

- **（报告读取）**——值是本平台从一份上传件里读出来的，而那一份是化验所出的基因报告。
  **不一定是他传的最后一份**：本平台在他上传的东西里认定一份作为这份档案的基因证据
  （读到过东西没有、是不是基因报告、解析有没有跑完、读出来的项多不多，都排在上传时间
  前面），基因这几项只从那一份读。他问「我上个月才传了新的，怎么还是老数字」，答案在
  这里。就算这样，也只说「这个数是本平台从你传的那份报告上读到的」——**读的是报告，不
  等于本平台替实验室复核过这个数**。
- **（转录自非基因报告文件）**——同样是本平台读出来的，但读的那一份不是基因报告：一份
  转抄了重复数的病历摘要，在基因报告什么都没读出来的时候会被认定成这份档案的基因证据，
  因为对一部分患者那是这个数字唯一的副本。**值照登，括号换成这一句**，但它换不来基因
  确诊：证据分级落在「仅有转录结果」，按重复数分的那几条指南建议也不发，换成「要看报告
  原件」那一条。所以护照上那几栏会一边印着数字、一边印着「未经基因确诊」——他要是问起来，
  这就是原因，不是页面自相矛盾。**别念成「这是化验做出来的」**，说「这个数是本平台从你传
  的一份材料上读到的，那份材料不是基因报告本身」。他手上真有化验报告的话，传上来这一段
  才会按报告写。
- **（管理员代填）**——本平台的人写的，什么时候写的记在护照的「字段来源」里。**诊断
  日期**那一行后面出现它是正常的：能代填的是「确诊年份」，它在白名单上，护照这一行的来
  源就是从「确诊年份」那条代填记录来的。但**别说「护照上这个日期就是管理员填进去的那个
  数」**——护照上可能印着 2019-05-03，而代填记录里是「2019」这个年份，日期本身另有来路
  （见第三条）。**分型 / D4Z4 / 甲基化后面出现则不正常**——代填写不进这几项，那条记录
  不是这个后台留下的。别动，先上报。
- **（非本人填写，来源不明）**——档案里有一条代填记录，但那条记录本身读不出来。能确定
  的只有一件事：**这个值不是他自己填的**。护照上那段「……不是本人填的」清单里会有对应
  的那个档案字段（诊断日期对应的是「确诊年份」）。别猜是谁填的，先上报。
- **（来源无法确定）**——值在档案里，本平台说不清它当初怎么进去的：没有代填记录，也分
  不清是他自己打的还是系统读取档案时从报告里补进去的。**别猜，也别替他认领**，尤其别说
  「这是你自己填的」——**本平台不记录谁打的字**，说「本平台这边没有别的来源记录」。
- **什么都没写、值是「—」**——护照上这一格是空的。这只说明本平台没有这个值，**不说明
  这项检查没做过**。

**三、更正在哪里：先分清他念的是哪一项，两条路不一样。**

- **诊断日期**——**不在报告页上**。报告详情页能修正的是报告名称、报告时间，以及
  分型 / D4Z4 重复数 / 单倍型 / 甲基化这几项基因结果；服务端的可修正字段白名单也是
  同一组，**里面没有诊断日期**。把他往报告页上送去改日期，他会白跑一趟。
  能改的地方是「我的 → 编辑资料」里的「确诊年份」（只收 4 位数字）：**在那儿填一个
  年份保存，护照上的诊断日期就变成那一年的 1 月 1 日。** 但**别说「护照上那个日期就是
  你填的确诊年份」**——护照上可能印着 2019-05-03，而那个框里是空的或是别的年份（日期
  也能从别处进到档案里，年份栏未必跟着）。他说「我那儿根本没填过年份」，不用怀疑他，
  按上面这句答：填一个，保存，日期就跟着走。
- **分型、D4Z4 重复数**——两条路都有：「我的 → 编辑资料」里有框，报告页上也能修正读数。
  按第一条不要替他改，请他自己在编辑资料里改最省事。
- **单倍型、甲基化**——「我的 → 编辑资料」里没有框，只剩报告那一条路。**报告详情页的
  修正表单上是有框的**（那张表把报告名称、报告时间和那几项基因结果一并画出来，识别没读到
  的那一格给的也是空框），但那一页画不画得出那张表，取决于那份报告此刻的状态，**而那一
  页也是唯一知道这件事的地方**——你这边看到的状态是快照，他点一次「重新识别」就作废。
  所以别替他保证有框，你能说的就到这里：

> 「这一项的更正在那份报告自己的页面上。你从最底下的「我的」进去，点「完整档案」，再点
> 「报告管理」，找到那一份点开看看——能不能改、怎么改，那一页会告诉你。如果打不开、
> 或者上面没有可改的地方，回来告诉我。」

**这条路径是照着 App 念的，别改口。** 「我的」是底部标签栏最右边那个，进去以后要点的是
「完整档案」那一行（不是「导出我的数据」），报告清单在它里面叫「报告管理」。**「我的」
下面没有一个叫「报告」的入口**，照那么念他会找不到。

**不要**替他描述按钮叫什么、在第几屏、点完会怎样，也不要断言「一定改得动」。

**他说他没有上传过基因报告**——那就没有报告页可以让他去，这句话别说。但**不要顺口
接成「那这一格本来就是空的」**：档案里那一份可能有值而报告没有（他在「编辑资料」里
打过，或者传过报告又删了）。先问他那一格印的是什么：是「—」，那确实没有这个值，让他
上传报告；印着值，就回到第二条，按那张表答，别猜。

**有一样确实改不回来，如实说，别承诺：** 基线档案里另存的那一份基因值，更正报告之后
不会跟着变。报告的读数只补档案里空着的格子，后台又不许写，而**导出（登记库导出、
全量 CSV）读的是档案里那一份**。患者早先保存过一次「编辑资料」，表单就会把它当时读到
的值一并写回档案，留下这么一份。碰到这种情况：说清楚导出里那一格还是旧值，然后记下来
上报——别把它和上面第三条混着讲。

另外：**后台这一页上基因那几栏显示「基线里没有」，不代表患者那边也是空的。** 患者端和
导出会用报告里的值补上空着的基因结果，这一页只显示基线里存的那一份。补进去的值来自
**本平台认定为基因证据的那一份上传件——不一定是他传的最后一份，也不一定是化验所出的
报告**——所以既别在电话里说「你没填」，也别说「以你最新那份为准」；先看这一页的报告
列表。

## 4. 上线顺序（相对 v2.5.0 §3.2 的差异）

v2.5.0 §3.2 的顺序照旧，插入下面这几步。**先做迁移 pre-flight，再拉栈**——api
容器的 CMD 自己会跑迁移（§1.1），栈起来之后再问库就已经晚了。

1. 备份（**确认落盘**，见 §1.1）
2. `git checkout` + `.env` 补齐（v2.5.0 §1.0-0 那个顺序陷阱仍然成立）
3. **迁移 pre-flight（趁旧栈还跑着，在宿主机上）**：`npm run db:migrate:status`，
   **带上 §1.1 那个 `DATABASE_URL=…` 前缀**。`orphan` 行必须在这里处理掉
   （v2.5.0 §2.1；退出码不替你看这几行，见 §1.1），并记下你的库停在哪一条（§1.1）
4. **同步反代的 `/s/*` 段**（§1.2）
5. `docker compose --profile prod build`（**必须 build，见 §1.3**）
6. `docker compose --profile prod up -d` —— **`--profile prod` 不能省**：caddy 是
   `profiles: ['prod']`，minio 是 `profiles: ['minio', 'prod']`，裸 `docker compose up -d`
   既不起反代也不起对象存储。迁移在这一步随 api 容器跑完，**不用再手工
   `npm run db:migrate`**（v2.5.0 §3.2 step 4 已经写了这件事；两条路径共用一把
   advisory lock，所以撞上也不会互相踩）。api 起不来时，迁移的输出在
   `docker compose --profile prod logs api` 里
7. **重建 caddy 让新 Caddyfile 生效**（§1.2）：
   `docker compose --profile prod up -d --force-recreate caddy`
8. `npm run db:migrate:status` 复核（**同样带 §1.1 那个前缀**）：021–027 应该全是
   `applied`（`drifted` 见 §1.1）
9. `docker compose exec api node /app/scripts/admin-role.mjs grant <你自己的手机号>`
   （裸号，且是 `exec` 不是 `exec -T`，见 §3.1）。**这个账号在手机/浏览器上如果已经登录
   着，现在退出登录再登进来**——不重登，「我的」里不会出现「后台」那一行，敲
   `/p-admin` 也会被换回 `/p-home`（§3.1）。下面的冒烟测试探不到这件事，它不碰后台
10. **配 cron（§2），并手动跑一次**
11. 冒烟测试 `scripts/smoke-test.sh`（含 `/s/` 那条断言——相对上一次部署是新的，
    它同时也是第 7 步生效了没有的验证）。**它不覆盖后台**：后台入口出没出来，只有你
    自己在第 9 步重登之后打开「我的」才知道

## 5. 上线后第一件会发生的事：所有人看到同意页

隐私政策版本 bump 了，所以**每个活跃账号下次打开 App 都会先进一屏「有条款需要你
确认」**。这是隐私政策 §9 承诺过的，不是故障。

盯这几件事：

- 客服/群里会收到「怎么突然要我同意」的问题。同意页第一屏就写了变了什么
  （管理员可以查阅和代填档案），可以直接引用那几句。
- **Web export 和 API 是分开发布的。** 如果只更新了 API 而前端还是旧 bundle，
  服务端会说「有个版本要确认」而旧 bundle 显示不出来。这个死循环代码里挡掉了
  （存的同意版本等于当前 bundle 版本时跳过），但**正确的做法仍然是两个一起发**。
- 点「暂不同意」的人不会被踢出去，也不会被限制功能——见 §0 最后那段。

## 7. 已知关注点

- **「暂不同意」不改变任何事**（§0）。待法务确认。
- **基线档案里存下来的那一份基因值，改不回来**（§3.4）。导出读的是档案，而档案里那
  一格两边都没有框可以清它。这一条讲的是导出里的那个副本，不是「这个值没法改」——
  更正报告本身是另一回事，能不能改由那份报告自己的页面决定，见 §3.4。
- **客服话术只说到「去那份报告的页面看」为止**（§3.4）。此刻能不能改，只有报告详情页
  知道；后台那一页看得到同一个状态字段，但它是快照，患者点一次「重新识别」就作废。
  手册里给的是怎么走到报告清单（我的 → 完整档案 → 报告管理），不是怎么改。上一版在
  这里写了按钮步骤，是错的。
- **诊断日期在报告页上没有更正入口**（§3.4）。它跟着档案里的「确诊年份」走，患者只能
  在「我的 → 编辑资料」里改。上一版把它和那几项基因结果混在一句里，会把人送去报告页
  上找一个不存在的栏位。
- **本次改动没有在真机微信浏览器里跑过。** 测试驱动的是控制器吐出的响应形态。
  前端以 web export 形式在微信 X5 内核里打开，这层没有覆盖到——上线后第一时间
  自己用微信打开一遍分享链接和同意页。
- `source_reported_total` 记录了但目前没有任何界面读它。
