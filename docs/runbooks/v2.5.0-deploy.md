# v2.5.0 部署手册

> 覆盖 `v2.4.0` → `v2.5.0` 升级路径：env 准备、迁移 013–020、prod 部署顺序、监控、回滚。
>
> **本手册取代 `docs/runbooks/v2.4.0-deploy.md`。** 那份手册对当前仓库已有多处失真：迁移范围写到 012、§4.1 的回滚命令会留下 `schema_migrations` 幽灵行、§1.1 的必填表没有 `NODE_ENV`、§1.3 指向一个不存在的 `apps/api/requirements.txt`、§3.2 step 7 让人去推 TestFlight / Play Store 而仓库根本产不出原生包。v2.4.0 手册保留为历史归档，**不要**照它部署 v2.5.0。
>
> 与通用 `docs/release-checklist.md` 配合使用：那份是每次发布都要过的门禁，本手册补 v2.5.0 specific 的步骤。

## 0. 这次发了什么

`v2.5.0` 没有新的患者侧功能面，主线是一轮 88 条 finding 的 deploy-readiness 审计闭合——即「测试全绿」和「生产能跑」之间那一层。按影响部署动作的顺序：

- **生产 fail-fast 真的覆盖到了它声称的东西**：新增 AI key 缺失、`postgres:postgres` 凭据（旧检查只认 `localhost` 字面串，在 compose 路径上是永久空转）、密钥强度、Baidu OCR 凭据、非 `.cn` 的 `AI_API_BASE_URL`（PIPL 跨境）、生产用本地磁盘存储、明文 MinIO 六道闸门。**这意味着一个在 v2.4.0 能起来的 `.env`，在 v2.5.0 可能起不来**——这是有意的，见 §1.1。
- **compose 变成了它文档里描述的那套部署**：`DATABASE_URL` 改成插值（此前 operator 填的托管库连接串被静默丢弃）、`POSTGRES_PASSWORD` 强制必填、`minio` 加入 `prod` profile、每个服务有 `mem_limit` 和日志上限、api 有 `stop_grace_period`、kb-service 不再拿到整份 `.env`。
- **readiness 不再把「KB 热了没」当成「API 能不能服务」**：`/api/healthz/ready` 只看 database + embedded OCR；KB / 对象存储 / 未配置的 AI key 走 `degraded`。compose 依赖放宽成 `service_started`。
- **`/api/healthz` 不再对公网吐内部细节**：生产下非 loopback 调用方只拿到 status，详情进日志并回一个 `requestId`。
- **迁移能真回滚了**：`migrate --down <id>` 把 `_down.sql` 和 ledger 删除放进同一个事务。
- **备份变成了代码**：`scripts/db-backup.sh` / `scripts/db-restore.sh`。
- **合规层从占位文本变成了真东西**：四份法律文档（用户协议、隐私政策、监护人同意、敏感个人信息处理单独同意）在 `apps/mobile/lib/legal-content.ts` 里成文，migration 019 建了接受记录账本 `legal_document_acceptances`，`POST /api/legal/acceptances` 写入 `(user_id, document, version, accepted_at)`，migration 020 加了 `withdrawn_at` 与 `POST /api/legal/acceptances/withdraw`（撤回同意），报告上传与健康数据写入路由前面挂了服务端的 `requireSensitiveDataConsent`，建档路由前面挂了 `requireGuardianConsentForMinor`。**这一段直接改变部署动作**：019 / 020 是本次的最后两条迁移，回滚它们会不可逆地删掉全部已记录的同意与撤回（见 §4.1）。
- 数据库迁移 **013–020**（v2.4.0 手册停在 012）。

完整清单见 [CHANGELOG.md](../../CHANGELOG.md) 的 `v2.5.0` 条目。

## 1. 部署前必备项

### 1.0-0 ⛔ 顺序陷阱：`git checkout` 之后、`.env` 补齐之前，你连日志都看不了

**这一段是实际部署时踩出来的，不是推演。**

compose 在执行**任何**子命令之前先做整份文件的插值。本次把
`POSTGRES_PASSWORD` 改成了没有默认值的必填项，于是从你 checkout 到 v2.5.0
的那一刻起，到你把这个键写进 `.env` 为止，这台机器上：

```
docker compose ps        ✗
docker compose logs      ✗
docker compose exec      ✗
docker compose down      ✗
docker compose config    ✗
```

**全部**失败，报的是同一句话：

```
error while interpolating services.kb-service.environment.DATABASE_URL:
required variable POSTGRES_PASSWORD is missing a value
```

容器还在正常跑，服务没有中断——但你失去了所有 compose 层面的观察和控制手段。
半夜遇到这个、又不知道原因，很容易以为栈坏了而去做更激烈的操作。

**这个窗口里要操作容器，绕开 compose 直接用 docker：**

```bash
docker ps                                    # 代替 compose ps
docker logs openrd-api-1 --tail 50           # 代替 compose logs
docker exec -i openrd-postgres-1 psql -U postgres -d fshd_openrd -c "..."
```

§1.0-a 的 `ALTER USER` 尤其要注意：它必须在 `.env` 补齐**之前**跑（要用旧密码），
也就是必然落在这个窗口里，**所以它不能用 `docker compose exec`**。

最省事的办法是把顺序倒过来：**先补 `.env` 里的 `POSTGRES_PASSWORD`，再 checkout**。
但 §1.0-a 要求先 `ALTER USER`，而 `ALTER USER` 又要用旧密码——所以真正安全的顺序是：

1. `ALTER USER`（用 `docker exec`，此时还没 checkout，用 compose 也行）
2. 写 `.env`
3. `git checkout v2.5.0`
4. 之后 compose 恢复正常

### 1.0-a ⛔ 从 v2.4.0 升级：先改数据库密码，否则整个升级卡死

**只有已经在跑 v2.4.0 的机器需要这一步。全新部署跳过。**

这一步必须在**动 `.env` 之前**做，因为它要用旧密码登录。做反了就没有回头路：

```bash
# 0) 先把新密码写进 .env 的 POSTGRES_PASSWORD（此时它还没生效，无害）
# 1) 再改库里的密码 —— 注意用 docker exec 而不是 docker compose exec，
#    见 §1.0-0：checkout 之后 compose 任何子命令都会失败
docker exec -i openrd-postgres-1 psql -U postgres \
  -c "ALTER USER postgres PASSWORD '<同一个值>';"
# 2) 立刻重启 api，让它拿到新密码
docker compose --profile prod up -d --no-deps api
# 3) 然后才是完整的 up -d --build
```

> ⛔ **顺序反过来会造成一次真实的服务中断。** 2026-08-03 实际部署时踩到过：
> 先 `ALTER USER` 再写 `.env`，中间那段时间里正在跑的 api 仍然拿着旧密码。
> **已经建立的连接不会断，所以看起来没事**——但连接池每次开新连接、健康检查
> 每 15 秒一次，用的都是旧密码。`/api/healthz` 立刻开始返回 503：
>
> ```
> "database":{"status":"error","detail":"password authentication failed for user \"postgres\""}
> ```
>
> 站点停了约二十分钟，直到新 api 起来才恢复。把 `.env` 写在前面、api 重启
> 紧跟在 `ALTER USER` 后面，这个窗口就只剩几秒。
>
> 「不重启容器所以服务不受影响」这个判断是错的，别照它推理。

**为什么**：`POSTGRES_PASSWORD` 只在数据卷**初始化那一次**生效。v2.4.0 的 compose 把凭据硬编码成 `postgres/postgres`，所以线上 `pg-data` 卷里存的就是 `postgres`；本次 compose 改成必填插值之后，你填的新值会进到容器的环境变量里，**而 Postgres 会忽略它**——卷已经存在了。于是 api 拿着新密码去连一个还认旧密码的库。

死锁在于两条路都堵死：

| 你填的 `POSTGRES_PASSWORD` | 结果                                                                      |
| -------------------------- | ------------------------------------------------------------------------- |
| 新密码                     | `FATAL: password authentication failed for user "postgres"`，api 无限重启 |
| 仍然是 `postgres`          | `validateProductionEnv` 拒绝 `postgres:postgres` 这对凭据，api 启动即退出 |

实测（v2.5.0 镜像 + 一个 v2.4.0 时期的卷，从 compose 网络上连）：

```
password=postgres     OK                                    ← 库里存的还是旧的
password=<新密码>      FATAL: password authentication failed
容器 env 里的 POSTGRES_PASSWORD = <新密码>                    ← 设了，但没用
```

注意 `docker compose exec postgres psql -U postgres` 在容器内部走的是 `trust`，任何密码都能进——**别用它来验证密码改没改成功**。要验证就从网络上连：

```bash
docker run --rm --network openrd_default -e PGPASSWORD='<新密码>' \
  pgvector/pgvector:pg16 psql -h postgres -U postgres -d fshd_openrd -tAc "select 'OK'"
```

### 1.0-b ⚠️ 升级时的 collation 漂移：可能要 REINDEX

同样只影响已有卷。`pgvector/pgvector:pg16` 的底层 Debian 换代之后，卷里记录的 collation 版本会和新镜像的 glibc 对不上，Postgres 每次连接都会打：

```
WARNING: database "fshd_openrd" has a collation version mismatch
DETAIL:  The database was created using collation version 2.41,
         but the operating system provides version 2.36.
```

**这不是噪音。** 文本列上的 B-tree 索引是按 collation 排序建的，排序规则变了之后索引里的顺序可能不再成立——查询会漏行，唯一约束可能放过重复值。本仓库这类索引有 **26 个**（`patient_documents.checksum`、`app_users.phone_number` 的唯一索引都在内）。

升级窗口内做完，再放流量：

```bash
docker compose exec postgres psql -U postgres -d fshd_openrd -c "REINDEX DATABASE fshd_openrd;"
docker compose exec postgres psql -U postgres -d fshd_openrd -c "ALTER DATABASE fshd_openrd REFRESH COLLATION VERSION;"
```

顺序不能反：先重建，再刷新版本号。反过来是把警告消掉而索引还是坏的。数据量小的时候 `REINDEX DATABASE` 几秒钟；它会持有锁，所以放在维护窗口里（§3.1）。

没有这条警告就不用做——版本一致时 Postgres 什么都不打。

### 1.0 前置：`.env` 必须存在，且必须有 `POSTGRES_PASSWORD`

`docker-compose.yml` 用 `env_file: [{path: .env, required: false}]`，所以 `.env` 缺失本身不再是硬失败。但 compose 里有三处**没有默认值**的插值，全都是同一个变量（postgres 服务一处，api 与 kb-service 的 `DATABASE_URL` 默认值里各嵌一处）：

```
POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env (local dev can use POSTGRES_PASSWORD=postgres)}
```

缺它 `docker compose config` 直接拒绝渲染，一个容器都不会创建。所以第 0 步永远是：

```bash
cp .env.example .env
# 然后按 §1.1 逐行填
```

> ⚠️ `POSTGRES_PASSWORD` **已经在 `.env.example` 里**（第 25 行，`POSTGRES_PASSWORD=postgres`，上面带六行 REQUIRED 注释）。生产要做的是**改掉那一行的值**，不是在文件末尾再补一行——dotenv 和 compose 插值都取最后一次出现，重复键的结果取决于你把新行插在哪里，而这一层区别在 `docker compose config` 的输出里看不出来。本地开发 `postgres` 这个值就够；生产必须换成真密码——`validateProductionEnv` 会独立拒绝任何仍带 `postgres:postgres` 的 `DATABASE_URL`，无论主机名是 `localhost` 还是 compose 内网的 `postgres`。
>
> ⚠️ **不要顺手把 `.env` 里的 `DATABASE_URL` 取消注释。** 模板里那一行是**故意注释掉的**：本次 compose 把 api 的 `DATABASE_URL` 改成了插值（此前 operator 填的托管库连接串被硬编码值静默丢弃），于是 `.env` 里的值会赢过 compose 的内网默认值——而 `localhost:5432` 在 api 容器里指的是容器自己。保持注释状态时两条路都对：本地直跑用 env.ts 的 localhost 默认值，compose 用 `@postgres:5432`。只有当数据库是**两边用同一个名字都能连到**的托管实例时，才在 `.env` 里显式写它；本地那些 host 侧脚本（`db:backup` / `db:restore` / `kb:prune`）需要 localhost 形态就单次传给它们。万一还是写成了 loopback，api 会带着点名 `DATABASE_URL` 的启动错误退出（`validateContainerTopologyEnv`，靠 compose 硬编码的 `OPENRD_IN_CONTAINER=true` 判断），而不是留下一串没头没尾的 `migrate.js` ECONNREFUSED 重启循环。

| `DATABASE_CONNECT_TIMEOUT_MS` | 10000 | —                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `SHUTDOWN_READINESS_DRAIN_MS` | 5000  | 有下限也有上限。下限：要大于负载均衡器的健康检查间隔（本仓库的 Caddy **不做**健康轮询——`Caddyfile` 里没有 `health_uri`，单副本部署下这 5 秒是纯等待，可以设 0）。**上限：必须小于 `SHUTDOWN_GRACE_MS`**，见下一行                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `SHUTDOWN_GRACE_MS`           | 20000 | 必须小于 compose 的 `stop_grace_period`（已设 25s），并且**必须比 `SHUTDOWN_READINESS_DRAIN_MS` 至少大 1 秒**。这个 deadline 从 t=0 起算、**包含**上面那段 drain，不是叠加：SIGTERM 时 force-exit 定时器按 GRACE 起算，`server.close()` 要等 DRAIN 之后才排上。两个值设反了（DRAIN ≥ GRACE），`server.close()` 和 `closePool()` 一次都不会执行，进程在 GRACE 到点时被 `process.exit(1)` 打断——正在流式回答的 SSE 连接从 socket 层被切断、pg 连接被丢弃，而日志上打出来的是「shutdown grace expired with connections still open」，读起来像慢客户端的锅。**这一条现在在启动时就会被拒**（env schema 的 cross-field 校验，非生产模式也生效），所以配错的后果是起不来，而不是下次 SIGTERM 才发作 |

其余可选项（`AI_MAX_TOOL_ROUNDS`、`AI_HISTORY_MAX_MESSAGES`、`AI_HISTORY_CHAR_BUDGET`、`OCR_MAX_PDF_PAGES`、`KB_FETCH_K` / `KB_FINAL_N` / `KB_MAX_PER_SOURCE`、`KB_MAX_CONCURRENT_SEARCHES`、`KB_SEARCH_QUEUE_WAIT_SECONDS`、`KB_PG_POOL_MAX`）现在**都在 `.env.example` 里带注释**，compose 也把它们显式列进了 `environment:` 块，不用翻代码。

> ⚠️ 其中 `KB_MAX_CONCURRENT_SEARCHES` 和 `KB_PG_POOL_MAX` 是一对必须一起动的旋钮：只抬其中一个，只是把排队从信号量挪进 psycopg 的连接池超时里。两份文件的注释都写了这条耦合，改一个就去改另一个。

### 1.4 Postgres extension 与 SSL

prod 数据库需要 `vector` 扩展：

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

托管 PG（RDS、Cloud SQL）通常要先在控制台把 `vector` 加进扩展白名单。自管 `pgvector/pgvector:pg16` 容器已预装扩展库，`db/init_db.sql` 在数据库**首次 init 时**就执行 `CREATE EXTENSION vector`。

> ⚠️ 注意 `db/init_db.sql` 里那行不是「非 compose 场景的幂等兜底」——`CREATE EXTENSION IF NOT EXISTS` 仍然要读控制文件，宿主上没装 pgvector 时它在 bootstrap 阶段就会失败，根本走不到 migration 006。这条注释本次已在 `init_db.sql` 里更正。

> ⚠️ **若 postgres 数据卷是在此修复之前建的**（init script 只在卷为空时跑一次），扩展不会自动补上，kb 会一直 unhealthy：
>
> ```bash
> docker compose --profile prod exec -T postgres \
>   psql -U postgres -d fshd_openrd -c "CREATE EXTENSION IF NOT EXISTS vector;"
> docker compose --profile prod up -d
> ```

**DB SSL**：`DATABASE_SSL_ENABLED` 单独控制，**不被 `NODE_ENV` 强制**。远程 / 托管 DB 必须显式 `DATABASE_SSL_ENABLED=true`（按需配 `DATABASE_SSL_REJECT_UNAUTHORIZED`）。compose 内部 postgres 走 docker 内网、不支持 SSL，自管栈保持 `DATABASE_SSL_ENABLED=false` **并设 `DATABASE_ALLOW_INSECURE=true`** 显式确认——否则 prod 启动 fail-fast。pool / migrate client / bootstrap admin client 三处共用 `resolvePgSsl`。

> **本次修正**：`ensureDatabaseExists` 以前无条件先连 `postgres` 维护库。托管 PG 上应用角色往往连不上它，结果 api 容器在碰 ledger 之前就 crash-loop，报错还指着一个 operator 没配过的库名。现在先试目标连接串，只有拿到 SQLSTATE `3D000`（invalid_catalog_name）才回落到维护库；密码错、路由不通这些照原样抛出。

### 1.5 对外暴露与 HTTPS（Caddy 反代）

患者数据必须走 HTTPS。`caddy` 服务（`prod` profile）做反代 + 自动证书：

- **域名**：`DOMAIN`（默认 `ai.fshdyouth.com`）的 A 记录指向服务器公网 IP。Caddy 用 HTTP-01 challenge 自动申请 + 续期 Let's Encrypt 证书。
- **安全组只放行 `80` + `443`**。**不要**放行 `4000` / `8080` / `5432` / `5010` / `9000`——它们在 compose 里绑 `127.0.0.1` 或只在内网。
- **路由**：`/api/*` → `api:4000`（含 SSE），`/*` → `web:80`。
- **安全响应头**（本次新增，Caddy 站点级 + `nginx.conf` server 级各一份）：`X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Permissions-Policy`、`Strict-Transport-Security: max-age=31536000; includeSubDomains`，静态站另加 `Content-Security-Policy: frame-ancestors 'none'`。
  - HSTS 是一年期承诺：浏览器见过之后一年内拒绝对本域走明文 HTTP。**故意没有 `preload`**——那个只能靠申请撤销。
  - CSP 只在 web upstream 的 `handle` 里设，不设站点级：站点级会**替换掉** helmet 在 `/api` 上已经发的那份更完整的策略。
- **部署命令必须带 `--profile prod`**：

  ```bash
  docker compose --profile prod up -d --build
  ```

  这一条命令现在能把**全部六个服务**拉起来：`postgres`、`kb-service`、`api`、`web`（无 profile，默认启动）+ `minio`、`caddy`（profile 分别是 `['minio','prod']` 和 `['prod']`）。

  > **本次修正**：`minio` 以前只在 `['minio']` profile 里，而手册 §4.3 又要求 prod 必须走 `STORAGE_PROVIDER=minio`。结果是整栈起来全绿、healthcheck 通过、Caddy 放进流量，然后每一次患者上传都在 connect 阶段 500——第一个信号是患者传不上 MRI 报告。现在 `--profile prod` 会带上它。**不需要**再叠一个 `--profile minio`。

- **移动端**：见 §3.2 step 6，**不要**去改仓库根 `.env`。
- **CORS**：`.env` 设 `CORS_ORIGIN=https://ai.fshdyouth.com`。

首次拉起后 `docker compose --profile prod logs -f caddy` 看到 `certificate obtained successfully` 即签发成功。

> ⚠️ **备案**：大陆区域的服务器，未备案域名的 80/443 入站会被拦，Caddy 的 HTTP-01 challenge 会一直失败、站点起不来，而日志里只会看到取证循环。部署前确认 `fshdyouth.com` 的 ICP 备案号，并确认站点页脚已渲染它。这也是 `docs/release-checklist.md` §1 的一条门禁。

`internal_test` 是**受控测试窗口**的显式选择，不是短信没就绪时的替代品：

- `OTP_TEST_PHONE_ALLOWLIST`：逗号分隔白名单。**只有**这些号能登录，其他号发码直接 403。号码可写裸号（`13922220001`）或带国码（`+8613922220001`），后端 `normalizePhone` 两种都能匹配。

- 护栏：prod/staging 下白名单为空或固定码非法 → 启动 fail-fast。验证码**不会**进 HTTP 响应。
- ⚠️ 固定码不像随机 OTP 那样一次性失效，它一直有效直到你改 env。**测试设备丢失或固定码外泄时立即轮换并重启容器。**

### 1.7 备份先行

**迁移前永远先备份**，而且现在这是一条脚本而不是一句嘱咐：

```bash
BACKUP_DIR=/mnt/offsite/openrd npm run db:backup
```

`scripts/db-backup.sh` 做了五件手打 `pg_dump` 不会做的事：

1. **绝对路径预检**：`BACKUP_DIR` 不是绝对路径直接拒跑。相对路径会解析到「脚本恰好从哪个目录被拉起」——对 `npm run db:backup` 就是仓库根，也就是把 PHI dump 写进工作区。错误信息里会给出它猜的绝对路径，可以直接复制。
2. **行数预检**：`app_users` 低于 `MIN_APP_USERS`（默认 1）或 `kb_chunks` 低于 `MIN_KB_CHUNKS`（默认 1）就拒绝出档；更重要的是**和上一份 dump 比**——每份 dump 旁边写一个 `.dump.meta`，下次跑会读最新那份，行数跌超过 `ALLOWED_ROW_DROP_PCT`（默认 10%）或数据库名变了就停在 `pg_dump` 之前。固定下限只挡得住空库，挡不住 `DATABASE_URL` 从 400 个患者的生产库漂到 2 行的 staging 库，而后者在任何「有没有」式的检查里都长得一模一样。确属真实下降（批量删除请求、故意重建语料）时用 `ALLOW_ROW_COUNT_DROP=1` 单次放行。
3. 先写 `.partial` 再改名，所以被中断的 dump 不会长得像一份完整备份。
4. 用 `pg_restore --list` 回读校验通过之后，才写 `.meta`、才允许 `RETENTION_DAYS`（默认 14）去清旧档；而且**清理另有一道闸**：新 dump 的 `app_users` 比上一份少哪怕一行，或者体积不到上一份的 60%，就跳过清理并在日志里说明原因。留着多余的档只费磁盘，删掉最后一份还有患者的档就是删掉患者。
5. `BACKUP_DIR` 落在工作区内时警告并自动丢一个自忽略的 `.gitignore`，PHI dump 不会被 `git add -A` 卷进去。

> 连接凭据走 `PGPASSWORD` 等环境变量而不是命令行参数，所以 dump 期间 `ps auxww` 里看不到生产数据库密码；`PGDATABASE` 也是解析 URI 得来的，不再是正则截取——一个没有路径段的 `DATABASE_URL` 会在这里明确报错，而不是把密码写进 dump 文件名和日志。

> `BACKUP_DIR` 必须是绝对路径，而且必须指到**宿主机之外**才算备份。和 `pg-data` 同一块盘上的 dump，扛不住任何一种真正会发生的故障。这条脚本是纯 shell，可以直接挂 host cron（脚本头部有 crontab 示例）。

恢复演练用 `npm run db:restore -- <dump> --into postgres://…/openrd_restore_drill`。默认拒绝任何已有业务行的目标库，`--force` 才覆盖——**在生产上永远不要带 `--force`**。

#### Pre-flight — `schema_migrations` 里有 `*_down.sql` 行吗？

PR #58 之前的 `migrate.ts` 会把 `011` / `012` 的 `_down.sql` 当 forward 跑掉，DROP 掉刚建的 CHECK + trigger，并往 ledger 写两条 `*_down.sql` 行。**任何在 PR #58（commit `bbd403f`）之前部署过 master 的环境都中招。** 从 v2.4.0 升上来的环境已经处理过；只有更老的环境需要这一段。

> 本次起 `npm run db:migrate:status` 会自己把这类行列成 `orphan` 并以非零退出码结束，所以下面这段 SQL 是双保险 / 排查用；不要因为「跑过 status 了」就跳过第 2、3 步的清理动作，status 只报告不修复。

```sql
-- 1) 看 ledger 有没有 _down 行
SELECT id FROM schema_migrations WHERE id LIKE '%_down.sql';
-- 期待：(0 rows)

-- 2) 有的话，把对应 forward 行一起删掉（schema 里 CHECK / trigger 也是空的，要重跑）
DELETE FROM schema_migrations
 WHERE id IN (
   '011_status_check_constraints.sql',
   '011_status_check_constraints_down.sql',
   '012_text_column_constraints.sql',
   '012_text_column_constraints_down.sql'
 );

-- 3) 重跑 forward
--   npm run db:migrate
-- 期待 stdout: Applied 011_… / Applied 012_…；_down 文件不该出现

-- 4) 验证 CHECK + trigger 到位
SELECT COUNT(*) FROM pg_constraint WHERE contype='c' AND conname LIKE '%_check'; -- ≥ 22
SELECT tgname FROM pg_trigger WHERE tgname='patient_followup_events_same_profile'; -- 1 行
```

### 2.2 KB 服务联通

```bash
# 未带 token
curl -X POST http://staging-kb:5010/multi \
  -H 'Content-Type: application/json' -d '{"question":"FSHD 是什么"}'
# 期望 401

# 带 token
curl -X POST http://staging-kb:5010/multi \
  -H "Authorization: Bearer $KB_SERVICE_TOKEN" \
  -H 'Content-Type: application/json' -d '{"question":"FSHD 是什么"}'
# 期望 200 + chunks

# 语料非空（本次新增的 readiness 门禁）
curl -s http://staging-kb:5010/health/ready
# 期望 200 + status ok。语料为空时是 503 + status "empty_corpus"，
# 不是 "error" —— 这两个的排查方向完全不同
```

> **为什么空语料要挡 readiness**：模型热了、检索链路全通、`/multi` 正常返回 0 条——而 `context-builder.ts` 把「零 chunk 且没有 failureReason」渲染成「（无内容）」，和「这个话题语料里确实没有」完全无法区分。结果就是一个全绿的新环境，对每一个 FSHD 患者说文献里查不到。探测结果非零后永久缓存（稳态零 DB 负载），零 / 未知每 30 秒重探一次，所以 `npm run kb:ingest` 灌完不用重启就会翻绿。探测**不确定**时（比如后端不支持行数查询）不拉黑 readiness。

并发检查（本次新增）：kb-service 换成了 `ThreadingHTTPServer`，`/multi` 由 `KB_MAX_CONCURRENT_SEARCHES`（默认 2，和 `KB_PG_POOL_MAX` 对齐）的信号量限流，排队超过 `KB_SEARCH_QUEUE_WAIT_SECONDS`（默认 20，故意低于调用方 30s 超时）返回 503 `kb_busy`。健康探针走的是廉价路径，**不会**再排在一次搜索后面。

### 2.3 核心功能端到端

按从浅到深跑：

#### A. 注册 / 登录 / OTP

- [ ] staging 手机号注册 → OTP 发送成功

#### B. 患者档案 + 文档上传

- [ ] 上传 MRI 报告（OCR `classifiedType: 'muscle_mri'`）→ 201 + DB 写入 `document_type = 'mri'`

- [ ] **本次新增**：上传一份接近 10 MB 上限的扫描件 → 应该能传完。超时预算现在按体积算（45s 固定 + 每 40 字节 1ms，上限 240s），此前是死的 60s，接近上限的文件无论重试几次都传不完

## 3. Prod 部署步骤

按部就班；任一步未通过不进下一步。

### 3.1 维护窗口决策

- 013 / 014 / 016 / 018 / 019 是加列、建表、建索引，当前数据规模下毫秒级（019 建的是空表）
- 015 / 017 的 `ADD CONSTRAINT` 取 ACCESS EXCLUSIVE 并做校验扫描；单 api 实例 + `up -d --build` 先停后起，没有并发写者
- 015 会改写 `patient_function_tests.unit` 的历史值（原文保留在 `unit_legacy`）
- **如果决定跑 011/012 的 `VALIDATE CONSTRAINT`**：全表扫描，放维护窗口
- **KB 模型权重**：warm-cache rolling restart ~30s。**首次 deploy 或 volume 重建**：拉 ~2GB 权重，3-5 min 起步。healthcheck budget 是 30 × 15s = 7.5 min。**本次起，超时不再拖垮整站**——api 只等 kb 的 `service_started`，KB 慢只降级 AI 问答。仍然建议 pre-warm：

  ```bash
  docker compose pull kb-service
  docker compose run --rm --no-deps kb-service \
    python -c "from sentence_transformers import SentenceTransformer; SentenceTransformer('BAAI/bge-m3')"
  ```

- **宿主机内存**：compose 现在给每个服务设了 `mem_limit`（kb-service 4g + `cpus: '2.0'`、api 3g、postgres 1g、minio 512m、web 128m、caddy 128m），上限合计 8.75 GiB。**最低宿主 8 GB**，这些是「超了杀这个容器」的阈值而不是预留量。设上限的意义是：KB warmup 撑爆内存时内核杀的是 kb-service 自己，而不是按 RSS 打分挑中 postgres。

1. **确认 `.env`**：`NODE_ENV=production`、`POSTGRES_PASSWORD`、§1.1 整张表。可以先干跑一次：`docker compose --profile prod config -q`（只做插值和校验，不启动任何东西）

   ```bash
   docker compose --profile prod up -d --build

   迁移随 api 容器 CMD 自动执行（`node dist/db/migrate.js && node dist/index.js`），并且在一个 advisory lock 里跑，所以手工 `npm run db:migrate` 和容器启动撞上不会互相踩。想 migrate-first 而不依赖 auto-run，就在这一步之前手工跑一次 `npm run db:migrate`。

### 3.3 上线后第一小时盯什么

先确认健康端点：

```bash
# 宿主机上（loopback，拿得到完整 payload）
docker compose --profile prod exec -T api \
  node -e "fetch('http://127.0.0.1:4000/api/healthz').then(r=>r.json()).then(j=>console.log(JSON.stringify(j,null,2)))"
```

> **注意**：从公网 `curl https://ai.fshdyouth.com/api/healthz` 现在只会拿到 `{status, ready, requestId, components:{<name>:{status}}}`。原始 pg 错误串、`http://kb-service:5010`、解析器在容器里的绝对路径、Python 版本、KB 的 `lastError` 一律不再进响应体——它们进日志，和回给调用方的 `requestId` 同一行。所以排查时**要么在宿主上走 loopback，要么按 requestId grep 日志**，不要指望公网响应告诉你原因。健康时不打日志（compose 探针 15 秒一次）。

各组件语义（本次调整）：

- `ready: false` 只可能来自 **database 或 embedded OCR 挂了**，或者正在 draining。这两个是「没有它任何请求都服务不了」的组件。
- `status: degraded` + `ready: true`：KB 挂了 / KB 正在 warming / `empty_corpus` / MinIO 连不上 / AI key 没配。**站点仍在服务**，但有东西坏了，要处理。
- `storage` 组件只在 `STORAGE_PROVIDER=minio` 时探测，探 `/minio/health/live`。**任何 HTTP 应答（含 403/404）都算可达**，只有连接失败 / DNS 失败 / 超时才算挂——托管 S3 兼容 endpoint 不会被误报为宕机。

然后盯这几项：

- API `5xx` 率：基线 +50% 以上立刻准备回滚
- `/api/profiles/me/documents/upload` 失败率
- `auth.register_failed` audit 行（`reason=exists_concurrent`）突增 = 有人在猜手机号
- SiliconFlow 调用量 + token 消耗：比 dev 估算高 2× 就关注
- KB service 容器 RSS：`mem_limit` 是 4g，逼近就是要么调大要么查泄漏（此前这条只能靠人盯，现在超了会被 cgroup 杀掉并由 `restart: unless-stopped` 拉起，日志里会有 OOMKilled）

### 3.5 全新部署：KB 语料 seed（空库才需要）

§3.2 是「升级既有 prod」的视角。**全新环境**跑完 migration 后 `kb_chunks` 是空的。**本次起这个状态会被 readiness 抓住**：kb-service 返回 503 + `status: "empty_corpus"`，api 的 `/healthz` 把它作为独立组件状态透出（不是笼统的 `error`），所以你会在部署当天就知道，而不是等患者反馈「AI 说文献里没有」。

kb-service 镜像里没有 ingest 脚本 / 源文档，没法在 prod 现场重新 ingest。正确做法是从一个已 ingest 好的环境整表搬 `kb_chunks`：

```bash
# 1. 源环境 dump：data-only
pg_dump -U <user> -d fshd_openrd -t kb_chunks --data-only --no-owner --no-privileges \
  | gzip > /tmp/kb_chunks.sql.gz          # 实测 9594 chunks / 164MB 表 ≈ 50-60MB gzip

# 2. 传到新机
scp /tmp/kb_chunks.sql.gz <新机>:/tmp/

# 3. 新机导入
gunzip -c /tmp/kb_chunks.sql.gz | grep -v '^SET transaction_timeout' \
  | docker compose --profile prod exec -T postgres psql -U postgres -d fshd_openrd -v ON_ERROR_STOP=1

# 4. 验证
docker compose --profile prod exec -T postgres psql -U postgres -d fshd_openrd \
  -tc "SELECT count(*) FROM kb_chunks;"
```

⚠️ **PG 版本兼容**：`pg_dump` 若是 PG17（macOS Homebrew 默认）而 prod 是 pg16，dump 头部的 `SET transaction_timeout = 0` PG16 不认，`ON_ERROR_STOP` 会中断导入。`grep -v` 滤掉即可。

导入写入 migration 006 建好的 hnsw 索引，随 COPY 增量维护，约 1 万行 2-5 分钟，无需 REINDEX。

> ⚠️ **别拿固定数字对答案。** 这份手册早先写「12352 chunks」，那是 2026-08 那次去重之前的数量；去重后源环境实测是 **9594 行 / 206 个 source_file / 表 164 MB**。语料会随 ingest 和 prune 变动，所以核对的方式是**在源环境跑一次 `SELECT count(*) FROM kb_chunks` 记下来，再和目标环境比**，不是和手册里的数字比。看到不一致就以为导入被截断、重导一遍，是这个数字造成的最可能的伤害。kb-service 实时查 pg，**导入完无需重启**——readiness 的语料探测在缓存未命中时每 30 秒重探一次，会自己翻绿。

> ⚠️ 源语料（`content/medical-kb/source/`，547 MB / 235 个文件）是 gitignore 的，目前只在一台开发机上。`scripts/kb-ingest.py` 和 `scripts/kb_parsers/` 都在仓库里，能重新 ingest——**前提是那份源语料还在**。把它纳入常规备份是一项独立的待办。

## 4. 回滚

### 4.1 Migration 回滚

**用 runner，不要手工 `psql < *_down.sql`。**

```bash
# 按倒序回滚。id 可以写 020、文件名 stem、forward 文件名或 _down 文件名
# 020 和 019 先看下面那两条警告——它们是本次仅有的「跑完就找不回来」的回滚
npm run db:migrate:down -- 020
npm run db:migrate:down -- 019
npm run db:migrate:down -- 018
npm run db:migrate:down -- 017
npm run db:migrate:down -- 016
npm run db:migrate:down -- 015
npm run db:migrate:down -- 014
npm run db:migrate:down -- 013
```

`--down` 在**同一个事务**里做两件事：跑 `_down.sql`，并 `DELETE FROM schema_migrations WHERE id = <forward 文件名>`。

> **为什么必须这样**：v2.4.0 手册 §4.1 让你 `psql $PROD_DB < db/migrations/012_..._down.sql`。那条命令不碰 ledger，于是回滚后 ledger 仍宣称 012 已应用，而 schema 里什么都没有。后续 roll-forward 时 `applied.has(file)` 直接跳过，**什么都不打印、退出码 0**，约束永久缺失而部署报告成功。这正是 PR #58 修掉的那一类静默失败，只不过是通过仓库自己文档里的回滚流程复现的。
>
> 另外那些 `_down.sql` 在本分支上已经不再自带 `BEGIN` / `COMMIT`（runner 会包），所以直接 `psql <` 跑是**非事务**的；`--down` 把事务还了回来。
>
> ledger 里没有对应行时 `--down` 会拒绝执行并提示 `--force`——那是给「已经按旧流程手工跑过 down 脚本、现在只需要清掉 ledger 行」的人用的。

**回滚前必须知道的四件事**：

- **020（撤回同意）**：`_down` 会 `DROP COLUMN withdrawn_at`。它**不是**把状态退回撤回之前，而是把「这个人撤回过」这件事抹掉——所有读同意的地方都过滤 `withdrawn_at IS NULL`，列一没，**已经撤回敏感信息处理同意的用户会重新被当成同意了**，闸门放行，他们的健康数据继续被写入。这是本次唯一一条回滚后会导致「继续处理已被撤回同意的敏感个人信息」的迁移。回滚前先导出并决定怎么处理这些人：

  ```sql
  \copy (SELECT user_id, document, version, accepted_at, withdrawn_at
           FROM legal_document_acceptances
          WHERE withdrawn_at IS NOT NULL) TO 'withdrawals.csv' CSV HEADER
  ```

- **019（同意账本）**：`_down` 会 `DROP TABLE legal_document_acceptances`。**每一条「谁在什么时候接受了哪一版协议」的记录都会消失，而且在 schema 的任何别处都不存在**——不像 015 有 `unit_legacy`、016 有可捞出来的 `deleted_at`，这张表没有影子副本。它同时是我们在监管问询时唯一能拿出来的同意证据。回滚前**必须**先 dump：

  ```sql
  -- 在宿主上：
  -- pg_dump "$PROD_DB" -t legal_document_acceptances --data-only \
  --   > legal_acceptances_$(date +%F).sql
  SELECT document, version, count(*) FROM legal_document_acceptances GROUP BY 1, 2 ORDER BY 1, 2;
  ```

  另外要有心理准备：表没了之后，服务端的 `requireSensitiveDataConsent` 会对**每一个老用户**在下一次上传报告时重新弹单独同意。这是安全的失败方向（宁可再问一次，也不假设同意过），但对患者是可见的回退——所以 API 版本要和 schema 一起回滚，别只回滚数据库。

- **016（软删除）**：`_down` 会 `DROP COLUMN deleted_at`。**所有被患者撤回的随访记录会立刻复活**，重新进入趋势线、首页叙述和 AI 检索。这个信息在剩下的数据里无法重建——`deleted_at` 一没，「这条被撤回过」这件事就不存在了。如果生产上已经有人用过撤回功能，**回滚 016 之前先把它捞出来存档**：

  ```sql
  SELECT 'function_tests' AS t, id, deleted_at FROM patient_function_tests WHERE deleted_at IS NOT NULL
  UNION ALL SELECT 'symptom_scores', id, deleted_at FROM patient_symptom_scores WHERE deleted_at IS NOT NULL
  UNION ALL SELECT 'followup_events', id, deleted_at FROM patient_followup_events WHERE deleted_at IS NOT NULL;
  ```

- **015（unit 归一化）**：`_down` 先 DROP CHECK（顺序不能反——CHECK 还在时往回写自由文本会 23514），再从 `unit_legacy` 还原 `unit`。它**不会**顺手删掉 `unit_legacy`：那一列就是恢复记录，而回滚恰恰是最可能需要用它两次的时刻。如果数据库是被**旧版 015**（没有 `unit_legacy` 那版）迁过来的，`_down` 会 RAISE 一条 WARNING 点名哪些数据无法恢复，并指向 §1.7 的迁移前备份。

其余四条（013 / 014 / 017 / 018）的 `_down` 都是 `DROP COLUMN` / `DROP TABLE` / `DROP INDEX`，无隐藏数据损失——但 014 掉的是 `account_deletion_requests`，那是删除权的合规账本，和 019 一样回滚前先 dump 一份。

> ⚠️ **必须严格倒序，一条都不能跳**——而且现在 runner 会替你把关：`--down <N>` 在开事务之前先看比 N 新的迁移还有没有应用着，有就点名拒绝（`… are still applied and must be rolled back first`）。这道检查存在的原因是跳着回滚会静默毁坏 schema：017/018 还在时直接 `--down 016`，016 的 `DROP COLUMN deleted_at` 会 CASCADE 掉 017 建的那个 partial 索引，而 ledger 里 017 仍写着 applied，于是 roll-forward 跳过 017，索引永久缺失而 `--status` 报一切正常。`--force` 能跳过这道检查，但只在你已经逐条确认过上面那些迁移不依赖被回滚的对象时才用——在生产上，先按顺序回滚永远比论证依赖关系便宜。

### 4.2 版本回滚

本仓库是 compose + Caddy，**不是 k8s**（v2.4.0 手册 §4.2 给的是 kubectl 示例，只是示意）。实际的回滚是按 git tag 重建：

```bash
git fetch --tags
git checkout v2.4.0
docker compose --profile prod up -d --build
```

三个自建服务（api / kb-service / web）没有 `image:` 键，compose 用 `<project>-<service>:latest` 标签，所以回滚靠重建而不是换 tag——比换 tag 慢，但是可执行且版本明确。`minio` / `postgres` / `caddy` 三个外部镜像都已固定版本（`minio/minio:RELEASE.2025-09-07T16-13-09Z`、`pgvector/pgvector:pg16`、`caddy:2-alpine`），重建不会漂移。

`KB_SERVICE_TOKEN` 留在 `.env` 里对旧版本无害。**回滚后不要手工移除**，否则 roll-forward 时新镜像会因缺 token 拒绝启动。

> ⚠️ **回滚到 v2.4.0 之前先想清楚 env**：v2.5.0 新增的三个确认位（`AI_CROSS_BORDER_ACKNOWLEDGED` / `STORAGE_ALLOW_LOCAL` / `MINIO_ALLOW_INSECURE`）和 `POSTGRES_PASSWORD` 在 v2.4.0 的 compose 里不存在，留着无害。反过来，v2.4.0 的 compose 会把 `DATABASE_URL` 硬编码回 compose 本地库——**如果你已经迁到托管 PG，回滚会把 api 指回本地空库**。这条是 v2.5.0 修掉的缺陷，回滚就会把它带回来。

### 4.3 数据回滚

如果迁移期间已有新写入，回滚老版本后新 status 值会变成「未知」。两个选项：接受不一致（老代码读到未知 status 默认按 `uploaded` 处理），或批量映射回去：

```sql
UPDATE patient_documents SET status = 'processed' WHERE status = 'parsed';
UPDATE patient_documents SET status = 'failed'    WHERE status = 'parse_failed';
UPDATE patient_documents SET status = 'uploaded'  WHERE status = 'needs_review';
```

#### 上传文档的备份策略

患者文档（PDF / 影像 / 基因报告）落地路径取决于 `STORAGE_PROVIDER`：

- **`local`**（schema 默认）：写在 named volume `api-uploads`。`docker compose down -v` 会清空它，等于永久丢失全部患者文档。**本次起，生产用 `local` 必须显式设 `STORAGE_ALLOW_LOCAL=true` 才能启动**——此前这是唯一一个完全不经过校验的存储配置，也是「谁都没动过设置」时的默认值。
- **`minio`**（推荐 prod / staging）：写在 bucket `MINIO_BUCKET_NAME`（默认 `medical-reports`），用对象存储自带的版本 / lifecycle / 备份机制。`--profile prod` 现在会一并启动 minio 服务。

如果迫不得已在 prod 用 `local`：

- 每天备份 volume：`docker run --rm -v openrd_api-uploads:/uploads -v /backup:/backup alpine tar czf /backup/uploads-$(date +%F).tar.gz -C /uploads .`
- 备份传到独立机器或对象存储
- `docker compose down -v` **绝对禁用**，只用 `docker compose down`

### 4.4 前端回滚

web export 是唯一的分发通道，所以「回滚移动端」就是 §4.2 的整栈回滚——`git checkout v2.4.0 && docker compose --profile prod up -d --build` 会重新导出旧版 bundle，患者刷新页面即回退。没有商店审核延迟，也没有「已安装用户还停在新版本」的问题。

这同时也是**不做原生分发的一个实际好处**，在真的启动商店分发之前值得记住：原生版本发出去就撤不回来，只能靠 hotfix。

- **`.env.example` 里 `DATABASE_URL` 是注释掉的，这是有意的**：本地直跑和 compose 需要的主机名不同（`localhost` vs `postgres`），注释掉才能让一份未改动的模板两边都能用。想显式写它，先读 §1.0 的第二条警告。（`POSTGRES_PASSWORD` 则**已经在**模板里，改值即可，不用补行。）
- **CI 覆盖到 web bundle，但不覆盖镜像**：`.github/workflows/ci.yml` 有三个 job——`API (lint, format, typecheck, test)`、`Mobile (lint, typecheck, test, web export)`、`Report manager (pytest)`——Node 固定 20、Python 固定 3.11（和两个镜像一致），mobile job 会用和 `Dockerfile.web` 相同的命令跑一次 `expo export`，所以 Metro 解析和静态渲染是有门禁的。**没有门禁的是 `docker compose build` 本身**：api 镜像里的 Python OCR 依赖、`Dockerfile.kb` 的 ML 依赖、nginx 层，第一次被构建仍然是在部署机上。发布前在本地过一遍 `docker compose --profile prod build`。另外 master 分支保护是否开了 required status checks 要去 GitHub 设置里确认，仓库文件看不出来。
- **法律文本已成文，但主体登记信息还是占位符**：`apps/mobile/lib/legal-content.ts` 现在是四份成文文档（用户协议 / 隐私政策 / 敏感个人信息处理单独同意 / 儿童个人信息处理规则与监护人同意），点名了 LLM 服务商（硅基流动 SiliconFlow，`api.siliconflow.cn`，DeepSeek-V3）、列了个人信息清单、目的、保留期和全部接收方；migration 019/020 + `POST /api/legal/acceptances`（及 `/withdraw`）记录 `(user_id, document, version, accepted_at, withdrawn_at)`，报告上传前面有服务端 `requireSensitiveDataConsent` 闸门，隐私设置页可查可撤回。**剩下的缺口是两个 `【待补】`**：`OPERATOR_LEGAL_NAME`（运营主体登记名称）和 §5 里的「服务商合同主体」。PIPL 第 17 条要求告知处理者名称，所以**这两个填完之前 `docs/release-checklist.md` §4 的隐私政策项仍然不打勾**——不打勾的原因是这两个占位符，不再是「文本还是占位文本」。
